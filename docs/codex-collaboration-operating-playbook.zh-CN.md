## 1. 目的与来源

这份手册总结了人与 Codex 在工程、研究、写作、理论构建、长任务监控和软件交付中反复形成的一组协作模式，并为它们统一命名。

它不是对聊天习惯做频率统计，而是对历史上确实使用过、并产生明显价值的方法进行回顾性综合。SCS、AlphaSchema、VPP、`stock_rec_v3` 和 Story Insight V7 等实例说明这些模式从何而来，但不构成它们已经获得普遍验证的主张。

目标是把原本有效但隐含的默契，变成一套简短、可复用的协作词汇。以后只需说出一个模式名称，就应足以确定：

- Agent 可以和不可以修改什么；
- 什么证据才算数；
- 一个观点如何升级为确认缺陷；
- 什么时候确实需要人类判断；
- 什么才叫真正完成。

整套方法可以压缩成一句话：

> 先用对抗审查和反例把问题定义硬，再把设计写成可执行契约；实施时隔离权限和影响，依靠真实运行及冻结实验验收，最后用结构化 handoff 和发布闭环完成交付。

## 2. 默认协作闭环

这些模式应当组成分阶段闭环，而不是塞进一个巨型提示词：

```text
观察与检查
  → 反驳第一次诊断
  → 建立权威契约
  → 端到端追踪设计不变量
  → 编写可执行计划
  → 在受限 write-set 内实施
  → 用冻结或真实证据验证
  → 接受、拒绝或升级
  → handoff 并闭环交付
```

并非每个任务都需要全部阶段。小型文档修改可以从范围检查直接进入交付；高风险能力则可能需要完整闭环。路由原则是：错误代价越高、越难发现、越容易被合理化，越需要治理；不要把治理变成无处不在的仪式。

## 3. 核心协作模式

### 3.1 只读对抗审查

**适用场景：** 用户要求 review；观察到的问题可能只是可疑症状；过早修改会污染诊断。

**执行契约：**

1. 只检查，不修改代码或权威状态。
2. 记录第一轮发现。
3. 用代码路径、运行证据、反例或故障注入反驳每一项发现。
4. 将其分类为确认缺陷、疑似缺陷或非缺陷。
5. 只有确认缺陷可以进入后续规划阶段。

确认缺陷不能只有观点。它至少应包含一条已定位的代码路径，以及一种有意义的证据基础：运行行为、可推翻实现的反例、被违反的契约或稳定复现的故障。

**调用语句：**

> 按“只读对抗审查模式”执行：先找可能的缺陷，再反驳自己的发现；只有反驳后仍成立的缺陷才进入方案，本轮不改代码。

**边界：** “这里还可以优化”不等于“这里存在缺陷”。审查必须保留这一差别。

### 3.2 权威基准到实现映射

**适用场景：** 正确性由论文、官方 API、标准、架构规范或其他权威来源定义。

**执行契约：**

1. 从权威来源提取相关定义与不变量。
2. 将其映射到实现中的契约、数据、算法、验证和产物。
3. 将现有测试映射到这些要求。
4. 设计能在现有测试之外推翻实现的反例。

```text
来源定义 → 实现位置 → 现有证据 → 缺失反例
```

这个模式适用于“测试全过，但语义正确性仍未建立”的情形。例如 AlphaSchema 原有 46 项测试全部通过，反例仍发现了前视、危险导入、无限循环、奖励错误和词表语义未生效等问题。

**调用语句：**

> 不要用现有测试定义正确性。先从权威来源提取契约，建立“来源定义—代码实现—测试证据”映射，再补充能够推翻当前实现的反例。

**边界：** 必须说明权威的适用范围。论文实验协议、API 文档行为和项目本地设计决策是不同类型的权威，不能静默混为一谈。

### 3.3 设计不变量的端到端审计

**适用场景：** 架构上系统应当以某种方式运行，但实际输出显示某个设计区分可能在下游丢失。

**执行契约：** 先确定设计不变量，再追踪所有可能保存、转换、混用或抹除它的层：

```text
配置
  → 数据生成
  → 资格门
  → 决策分
  → 晋级/路由
  → 运行时行为
  → 报告/导出
  → 测试
```

不能因为某一层出现了正确字段或公式，就判定不变量已经实现。只有目标语义贯穿完整链路，才算完成。

**调用语句：**

> 按“设计不变量审计”检查。把这个设计意图从配置、数据、门控、评分、晋级、运行时、报告到测试完整追踪，不能用局部实现证明端到端成立。

**边界：** 如果报告错误的原因是上游已经抹除了关键区分，只改报告属于症状层修复。

### 3.4 证据链根因诊断

**适用场景：** 运行描述强烈但含混，例如“系统坏了”“门控全拒绝”“因子完全失效”。

**执行契约：** 从原始输入一路追踪到运行产物、状态字段、决策逻辑和报告，至少分别判断：

- 执行链路是否真的停止；
- 资格门或策略门是否真的失败；
- 信号是零命中，还是仅仅退化；
- 是否触发了 fallback；
- 报告是否夸大了状态；
- 被同时引用的指标是否属于同一评价对象和时间尺度。

输出必须同时给出 **代码定义上的结论** 与 **生产语义上的结论**；二者可能不同。

**调用语句：**

> 按证据链诊断：从原始数据和运行 artifact，一直追到状态、决策和报告。分别给出代码定义上的结论和生产语义上的结论。本轮先诊断，不修复。

**边界：** 如果底层结果仍然违反设计不变量，修正文案并不能关闭任务。

### 3.5 可执行计划契约

**适用场景：** 实施涉及接口、数据契约、兼容性、多文件修改或有意义的权限边界。

**执行契约：** 规划与修改必须分阶段。编辑之前，计划至少定义：

- 摘要和目标结果；
- 公共接口与数据契约；
- 实施变更与允许的 write-set；
- 兼容性与迁移行为；
- 测试计划与真实运行证据；
- 假设和未决选择；
- 明确不做什么及禁止事项；
- 回滚或恢复路径；
- 失败条件；
- Definition of Done。

计划不是对未来工作的散文式预测，而是可审查的实施契约。另一任务或另一个 Agent 应当能够执行它，而不必擅自补造产品决策。

**调用语句：**

> 先生成可执行计划，不写代码。明确接口、数据契约、兼容性、允许范围、非目标、验收证据、失败条件、回滚方式和 Definition of Done；确认后再实施。

**边界：** 计划获批只授权其中明确写出的 write-set 和行为，不授权顺手重构。

### 3.6 冻结边界的通用化实验

**适用场景：** 针对已知失败改进 Agent、启发式策略、因子或算法时，可能对 case、数据库、seed 或问题族过拟合。

**执行契约：** 在确认性评估前，冻结数据、样本、搜索空间、策略边界、评价流程和 discovery 截止点。实验 profile 与通用 profile 必须分离。失败 case 可以暴露通用风险，但不能直接变成 case 特例规则。

三类数据承担不同职责：

- **Discovery：** 产生假设；
- **Validation：** 选择或稳定通用机制；
- **Blind test：** 在代码和标准冻结后估计迁移能力。

重命名测试或复跑同一批 seed 可以发现明显记忆，却不能排除统计过拟合。冻结代码后使用新的 blind cohort 才是更强的检验。

**调用语句：**

> 按“冻结边界的通用化实验”执行：冻结数据、样本、搜索空间、策略和评价；分离实验与通用 profile；失败 case 只用于发现通用风险；最后用新 blind cohort 验收冻结代码。

**边界：** 看到测试结果后新增的条件，只能属于下一轮探索，不能计入本轮确认性结果。

### 3.7 零影响研究 Sidecar

**适用场景：** 新因子、Agent 能力或自动决策有潜力，但尚无资格影响生产。

**执行契约：** Sidecar 可以生成假设、预测和完整账本，但必须保持零生产权限。典型控制包括：

- 强制贡献值或 `factor_value` 为零；
- 禁止影响排名、持仓、交易或权威状态；
- 不发布 production pointer；
- 只允许在 discovery 窗口探索；
- 冻结后只允许删减、放宽或合并，不能事后增加条件；
- 必须经过独立验证并满足预先定义的晋级门槛，才允许升级权限。

**调用语句：**

> 新能力先按“零影响研究 Sidecar”实现：允许生成 hypothesis 和完整账本，但不得影响生产结果；冻结后独立验证，只有通过预先定义的晋级门槛才扩大权限。

**边界：** 只有零影响被机械强制并且可审计，“shadow mode”才有实际意义。

### 3.8 Planner–Executor–Validator–Authority 分离

**适用场景：** 修改涉及权威状态、生成产物、自动修复或高风险决策。

**执行契约：**

| 角色 | 可以做 | 不可以做 |
|---|---|---|
| Planner | 提出意图、范围、前置条件和变更蓝图 | 直接修改权威状态 |
| Executor | 在隔离环境中执行已授权 write-set | 扩大范围或自创新权限 |
| Validator | 按明确验收标准测试候选结果 | 暗中替执行器修补答案 |
| Authority | 接受、拒绝或晋级已验证候选 | 隐式让渡最终接受权 |

所有 post-render 语义修改都应经过受治理的修改通道。哈希、CAS、格式化和机械导出等确定性派生，应继续由确定性代码完成，不应为了形式而交给更多 Agent。

**调用语句：**

> 按“规划—执行—验证—准入分离”设计。Planner 不改权威状态，Executor 不扩大 write-set，Validator 不替 Executor 补答案，最终接受权留在领域 Authority。

**边界：** 分离解决的是互不相容的权限，不是追求最多的 Agent 或进程数量。

### 3.9 持续真实运行

**适用场景：** 长任务必须被持续监控，直到真实产物满足运行验收门槛。

**执行契约：** 启动前先定义：

- 硬失败与硬成功 Gate；
- 可恢复失败；
- 可报告但不阻断运行的软债务；
- 稀疏检查频率；
- attempt、failed、abandoned 条件；
- 允许修复的范围；
- 清理与最终终止条件。

按固定且有意义的频率检查，不逐分钟制造叙事噪音。只修稳定复现的架构缺陷。修复后从新版本进行一次真实运行，并验收其真实产物。禁止用 fake、replay、手工修改数据库或 CAS 的方式模拟成功。

**调用语句：**

> 按“持续真实运行模式”执行：定义硬失败、可恢复失败、软债务、检查频率、修复权限和终止条件；持续到真实产物满足硬验收，不能把进程退出当成成功。

**边界：** 完成状态包括产物完整性、lineage、export、进程状态与配置清理，而不仅是退出码为零。

### 3.10 结构化 Session Handoff

**适用场景：** 工作将转移到新的 Codex 任务；长任务会跨越当前 session；另一个执行者需要在不重建完整项目历史的情况下继续。

**执行契约：** Handoff 是状态差量，不是背景散文。它应包含：

- 当前基线分支和 commit；
- 已确认事实与当前状态；
- 权威文档和 artifact 位置；
- 已完成与未完成工作；
- 范围和禁止事项；
- 严格排序的下一步动作；
- 验收与终止条件。

长期规格应存放在版本化文档中。Handoff 只引用这些文档，并携带当前状态、证据和差量。

**调用语句：**

> 生成一个新 session handoff，按“状态、证据、边界、未完成事项、执行顺序、验收、禁止事项”组织。引用版本化规格，不要重复背景散文。

**边界：** 如果新任务无需重新发现已确定事实，也不会静默扩大范围，就说明 handoff 有效。

### 3.11 最小充分人类问题

**适用场景：** Agent 已经穷尽安全且在范围内的推进方式，必须获得一个由人控制的变量才能继续。

**执行契约：** 只有下一步至少涉及以下一项时，才应询问人类：

- 新权限或凭据；
- 扩大已批准的修改范围；
- 不可逆或有实质风险的外部动作；
- 实质产品、价值、预算或品味选择；
- 无法从环境获得的信息。

只问一个能注入缺失变量并恢复自治的问题，不要把整个任务退回给用户。

**调用语句：**

> 除非需要新权限、扩大范围或实质产品选择，否则自行推进。确实阻塞时，只问一个能够解锁下一步安全动作的最小问题。

**边界：** 状态更新、不确定性或实现困难本身，都不是升级求助的充分理由。

## 4. 两个辅助模式

### 4.1 分维度写作审改

先完成一份连贯初稿，再用相互独立的 lens 审改。价值来自每轮承担不同职责，而不是重复五次通用润色：

1. 定义、范围和边界；
2. 证据与 claim hardness；
3. 反例、可证伪性和局限；
4. 实践意义与可操作性；
5. 双语、结构、链接、渲染和发布一致性。

每一轮都必须有权拒绝或弱化主张，而不仅是改善语言。

**调用语句：**

> 先完成全文，再按五个独立 lens 审改：边界、证据、可证伪性、可操作性与发布一致性。

### 4.2 发布闭环

本地修改只是中间状态。只要任务包含发布，交付链路就是：

```text
scope diff → tests → branch → commit → push → PR → CI
  → merge → cleanup → 验证 main 与工作区状态
```

真正重要的不是 Git 命令本身，而是完整性规则：

- 只暂存任务范围内的文件；
- 保留用户的其他修改；
- 如实披露无关测试失败；
- 不绕过受保护检查来制造绿色结果；
- 合并后验证本地、远端和分支清理状态。

**调用语句：**

> 完成发布闭环：核对范围 diff，运行测试，通过受保护路径发布，CI 通过后合并，清理并核验最终 main/工作区状态。

## 5. 模式标签速查

| 短标签 | 含义 |
|---|---|
| 只读对抗审查 | 找可能缺陷、反驳缺陷，本轮不修改 |
| 权威基准映射 | 来源定义 → 实现 → 测试 → 反例 |
| 设计不变量审计 | 跨配置、数据、决策、运行时和报告端到端追踪 |
| 证据链诊断 | 区分真实故障、门控失败、fallback/降级和报告误导 |
| 可执行计划 | 先写实施契约，确认后执行 |
| 通用化防过拟合 | 冻结边界、分离 profile、使用新 blind cohort |
| 零影响研究 Sidecar | 先生产研究证据，不影响生产 |
| 受治理修改闭环 | Blueprint → 隔离执行 → 验证 → 接受/拒绝 |
| 持续真实运行 | 硬/软门控、稀疏监控，直到真实终止条件 |
| Session Handoff | 生成可以直接开启新任务的状态包 |
| 最小充分求助 | 只在真正阻塞时问一个最小问题 |
| 分维度写作审改 | 用相互独立的质量维度审查完整初稿 |
| 发布闭环 | 测试、发布、合并、清理并核验最终状态 |

## 6. 推荐组合

| 任务形态 | 模式顺序 |
|---|---|
| 含混的工程故障 | 只读对抗审查 → 证据链诊断 → 设计不变量审计 → 可执行计划 |
| 论文或 API 复现 | 权威基准映射 → 反例 → 冻结边界实验 → 可执行计划 |
| 高风险新能力 | 零影响 Sidecar → 冻结验证 → 受治理晋级 |
| 自动语义修复 | Planner–Executor–Validator–Authority 分离 → 真实验证 → 接受/拒绝 |
| 长时间生产式运行 | 持续真实运行 → 只修稳定故障 → 结构化 handoff |
| 理论或研究写作 | 完整初稿 → 分维度审改 → 双语一致性检查 |
| 仓库交付 | 范围内实施 → 测试 → 发布闭环 |

这些是默认组合，不是强制仪式。通常应选择能够保存权限、证据与可恢复性的最小组合。

## 7. 可复用产物模板

### 7.1 确认发现记录

```text
发现：
分类：确认缺陷 | 疑似缺陷 | 非缺陷
被违反的权威或不变量：
已定位代码/产物路径：
运行或测试证据：
已尝试的反驳：
反驳为何失败或成立：
影响边界：
建议下一阶段：停止 | 继续调查 | 进入规划
```

## 8. 协作层 Definition of Done

Agent 输出了文字、修改了文件或结束了进程，都不等于任务完成。根据任务风险，真正完成至少意味着：

- 所声称的问题经过了适当的对抗审查；
- 实施没有越过权限和 write-set；
- 目标不变量端到端成立；
- 验证证据有能力推翻结果，而不只是支持结果；
- 生产性结论来自真实产物，而非模拟状态；
- 剩余不确定性和软债务被明确记录；
- 下一位执行者可以从紧凑、版本化的状态继续；
- 用户要求的发布路径已经完整闭环。

这就是这套协作方式的实践特征：人负责治理真正重要的变量，Codex 负责让其余工作持续向前，并且始终携带证据、受边界约束、可以恢复。
