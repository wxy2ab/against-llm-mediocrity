# 任务接入与指南路由

状态：第一批操作指南

受众：编码 Agent、Agent Runtime 与操作者

基础：[Agent 五旋钮操作规范](./agent-five-knob-operating-guidelines.zh-CN.md)

English：[Task Intake and Guideline Routing](./task-intake-and-guideline-routing.md)

## 1. 目的

每个任务开始时都使用本指南。它的目标是防止 Agent 高质量地完成了错误的任务。

接入结果必须明确：

```text
用户要求的结果
任务类型
授权边界
权威来源
写入范围
验证边界
交付边界
停止与升级条件
```

当 Agent 能准确说明“可以检查什么、可以修改什么、什么证据足以宣称完成”时，任务接入才
算结束。

## 2. 判断用户要求的结果

根据用户要求的**状态转移**分类，不根据请求里出现的名词分类。

| 类型 | 用户可见结果 | 默认授权 |
|---|---|---|
| 回答 / 解释 | 有证据支持的解释 | 只读 |
| 检查 / 报告 | 当前状态说明 | 只读 |
| 诊断 | 已定位的原因和证据 | 只读 |
| Review / 审计 | 按严重性排序的发现 | 只读 |
| 修改 / 修复 | 边界明确的缺陷被消除 | 有范围写入 |
| 构建 / 功能 | 新行为被实现 | 有计划写入 |
| 重构 | 结构改变、行为保持 | 有计划写入 |
| 迁移 | 旧状态经过兼容计划进入新状态 | 受治理写入 |
| 验证 | pass/fail/readiness 裁决 | 除非要求测试产物，否则只读 |
| 操作 | 外部或有副作用状态改变 | 明确限定的操作授权 |
| 交付 | Commit、PR、发布或公开 | 明确交付授权 |
| 监控 | 持续观察直到终止条件 | 只读的持续授权 |

请求同时包含多种类型时，保持顺序：

```text
检查 → 诊断 → 修改 → 验证 → 交付
```

后面的阶段不能取消前面阶段所需的证据。

## 3. 建立授权边界

写入之前回答：

1. 哪些仓库、服务、文件、记录或外部系统在范围内？
2. 请求是只读、允许实现，还是允许交付？
3. 是否涉及破坏性、不可逆、公开、财务或人际副作用？
4. 哪些已有用户修改必须保留？
5. 哪些决策仍然只能由用户做出？

授权不会静默扩张：

- “诊断”不等于授权修复；
- “修复”不等于授权发布；
- “准备 PR”不等于授权合并，除非用户明确要求；
- 能访问某个系统不等于可以修改其中所有内容；
- 紧急不等于可以采用破坏性捷径。

只有假设可逆、位于已声明范围内、且不会实质改变结果时，才可以先按合理假设继续。会影响
设计或结论的假设必须明确说明。

## 4. 确认权威来源

优先级：

```text
用户明确提供的产物
→ 仓库本地指令和当前状态
→ 可执行代码、schema、测试和生成 manifest
→ 已连接的一方权威系统
→ 官方外部文档
→ 二手解释
→ 模型记忆
```

来源冲突时按权威性和时效性裁决，不按叙述的自信程度裁决。

建议记录：

```json
{
  "task_id": "stable-id",
  "requested_outcome": "...",
  "task_class": ["diagnose", "change"],
  "scope": ["repo/path"],
  "non_goals": ["..."],
  "authority": {
    "read": ["..."],
    "write": ["..."],
    "deliver": []
  },
  "authoritative_sources": ["..."],
  "verifier": ["..."],
  "stop_conditions": ["..."]
}
```

简单任务可以不落盘。多文件、长时间、多 Agent、高风险或需要恢复的任务应持久化。

## 5. 选择主指南

每次选择一份主指南：

```text
代码库陌生或影响范围不确定
  → 代码库侦察与影响分析

用户要求原因，没有要求修复
  → 故障诊断与根因定位

缺陷可复现且边界明确
  → 局部修复与 Bug Fix

新增行为 / 结构改变 / 兼容状态转移
  → 功能、重构与迁移交付

被改进对象本身是另一个 Agent
  → Agent 诊断与改进
```

只有当附加指南会改变证据、状态转移或验证方式时才加载。不要为了“完整”加载所有指南。

## 6. 判断澄清是否真正阻塞

能够从工作区或权威系统安全发现的信息，不要先问用户。

下列情况可以声明假设并继续：

- 选择可逆；
- 不同选项不会实质改变结果；
- 仓库已有明确惯例；
- 等待答案时仍有独立工作可做。

下列情况必须停止并询问：

- 不同答案会形成实质不同的产物；
- 缺少外部操作或破坏性操作授权；
- 涉及用户的价值、政策、品味或责任决策；
- 无法确认哪个产物是权威来源；
- 继续可能覆盖或暴露用户数据。

只询问最小充分变量，不要让用户重新描述整个任务。

## 7. 行动前定义完成

把“完成”翻译成可观察谓词：

```text
用户要求的行为存在
AND 相关回归行为保持有效
AND verifier coverage 与任务匹配
AND 没有未授权 collateral change
AND 必要产物已持久化
AND 用户要求的交付动作已完成
```

区分：

| 状态 | 含义 |
|---|---|
| Implemented | 修改已经存在 |
| Verified | 约定检查已经通过 |
| Delivered | 要求的 commit/PR/release/公开已经完成 |
| Blocked | 缺少必要的外部决策或授权 |
| Ungated | 产物存在，但没有运行足够的 verifier |

不得合并这些状态。

## 8. 常见接入失败

| 失败 | 修正 |
|---|---|
| 根据请求中最新出现的名词行动 | 重述用户要求的状态转移 |
| 把诊断当作写入许可 | 只返回证据 |
| 检查本地证据前先问宽泛问题 | 先检查，再询问剩余变量 |
| 一行可逆修改也加载大型工作流 | 走轻量路径 |
| 把局部修复扩张为清理战役 | 保持 non-goals 和写入范围 |
| Tool 返回成功就宣称完成 | 检查完成谓词 |
| 隐藏假设 | 公开影响设计或解释的假设 |

## 9. 快速接入检查表

```text
[ ] 用户究竟要求什么结果？
[ ] 这是回答、诊断、Review、修改、验证、操作还是交付？
[ ] 我可以读、写和公开什么？
[ ] 哪些已有修改或状态必须保留？
[ ] 哪个来源是权威来源？
[ ] 应使用哪份主指南？
[ ] 哪个 verifier 决定完成？
[ ] 什么情况必须停止或询问？
[ ] 不澄清是否仍可安全推进？
```

## 10. 交接

任务接入完成后，进入被路由的指南，或者报告真实 blocker：

```text
Route：

Scope / non-goals：
Authoritative sources：
Verifier：
Assumptions：
Blocking variable（如有）：
```
