# 状态治理智能体范式

## SGAR：长程 Agent 的硬状态治理工作稿

**状态：** 工作稿  
**缩写：** SGAR  
**英文名：** State-Governed Agent Regime  
**相关工作稿：** [知识治理](knowledge-governance-llm-systems-local-alignment.zh-CN.md)、[审计工程](audit-engineering.zh-CN.md)、[人类协助型操作失配](human-assist-operational-mismatches.zh-CN.md)、[治理式人机协作](governed-human-ai-collaboration.zh-CN.md)

## 摘要

**状态治理智能体范式**，英文可写作 **State-Governed Agent Regime**，缩写为 **SGAR**。它指的是这样一种 agent 治理体制：agent 的操作状态不再只存在于 LLM 上下文、记忆、摘要或自我叙事中，而是被外部化为**硬状态**——一种可验证、可更新、可恢复、可审计并具有治理权威的状态记录。

SGAR 的核心判断是：agent 不是"会调用工具的 LLM"。可靠的长程 agent 是一个在状态中行动、并通过受治理状态转移推进目标的系统。

LLM 上下文可以描述状态、记住状态、总结状态，也可以模拟连续性。但上下文本身不是状态权威。它更像一个叙事工作区。SGAR 的核心动作，是把 agent 的运行基础从"上下文里维持的叙事连续性"转移到"外部硬状态治理"。转移之后，系统当前承认什么、哪些行动可执行、什么证据能验证进展、任务是否真的被推进——这些都不再依赖上下文叙事，而由硬状态裁决。

SGAR 不宣称自己能保证形而上意义上的"真正因果"。更精确的说法是：SGAR 建立 **操作场景**，让 action 获得任务意义，让后果表现为可观察的状态差异，并让长程行为变得可审计、可恢复、可治理。

## 1. 核心命题

SGAR 的核心命题可以写成：

> 硬状态建立操作场景，场景赋予 action 任务意义；action 通过状态转移获得因果位置；agent 通过状态-行动-结果链条获得可治理的长期行为。

没有硬状态，系统仍然可能表现出 agent-like behavior：它会写计划、调用工具、循环执行、修订草稿、解释进展。但只要"我在哪里""什么是真的""什么已经完成""下一步能做什么"这些状态权威仍然只存在于 LLM 的当前上下文和自我解释中，系统本质上就仍是增强型 LLM 应用，而非可靠的长程行动系统。

SGAR 把运行问题从：

```text
LLM 下一步应该说什么或做什么？
```

改写为：

```text
在当前被承认的硬状态下，哪些行动可执行？
什么观测算作证据？需要什么验证？
哪个状态转移可以被提交？
```

## 2. 为什么上下文不是 Agent 状态

严格说，LLM 在操作意义上是无状态的。它接收上下文并生成续写。它可以在上下文里表示历史事实和承诺，但一旦上下文被改写、压缩、截断、矛盾信息污染或重新解释，这些表示就没有独立权威。

真正的问题不是 LLM 能不能 **模拟** 状态——它经常可以。真正的问题是：状态裁决权到底在哪里。

在上下文中心型 agent 中，LLM 往往同时承担：

- 规划者；
- 执行者；
- 观察者；
- 记账者；
- 审计者；
- 验收者；
- 治理者。

这种角色混合会带来可预期的稳定失败：虚假完成、自我合理化、忘记约束、目标替换、阶段识别不稳定，以及看起来很忙却无法可靠推进任务的行动循环。

SGAR 切开这组权力：

```text
LLM 层：理解、提案、探索、实现、解释
硬状态层：定位、约束、验证、提交、恢复、审计
```

LLM 可以提议某个状态转移已经发生。治理层决定这个转移是否被系统承认。

## 3. 软状态与硬状态

| 维度 | 软状态 | 硬状态 |
|---|---|---|
| 常见形式 | context、memory、summary、retrieval | 外部治理层 |
| 主要功能 | 帮助 LLM 理解背景 | 决定系统当前承认什么 |
| 权威性 | 低，偏建议性 | 高，偏操作性 |
| 稳定性 | 可改写、可压缩、选择性召回 | 独立于单次推理和单个上下文 |
| 失败模式 | 漂移、重释、叙事顺滑化 | 如果设计错误，会固化错误抽象 |
| 正确位置 | 认知辅助 | 状态权威 |
| 简短定义 | 类似 belief 的支持 | 类似 commitment 的记录 |

SGAR 不否定 memory。它让 memory 回到正确位置：

```text
Memory tells the agent what may be relevant.
Hard state tells the agent what is currently true for governance.

记忆告诉 agent 哪些东西可能相关。
硬状态告诉 agent 系统现在承认什么。
```

SGAR 也不否定 planning。但计划不是进度。SGAR 区分三件事：

1. **Plan：** 打算做什么。
2. **Action：** 实际做了什么。
3. **State transition：** 经过证据和验证后，系统是否承认状态改变。

agent 不能因为计划里写了"完成验证"，就等于真的完成验证。验证必须被执行，证据必须被附着，状态转移必须被提交或拒绝。

## 4. 操作场景

action 的任务意义只存在于状态之中。同一个工具调用、消息、文件编辑或实验，在不同操作状态下含义完全不同。

例如，"跑测试"可能意味着：

- 实现前的 baseline discovery；
- 补丁后的验证；
- 旧失败后的回归审计；
- 升级给人之前的证据收集；
- 回滚后的验证。

行动字符串相同，任务意义不同，因为状态不同。

因此 SGAR 把 action 写成：

```text
在状态 S 中采取行动 A，产生观测 O，
应用验证 V，然后提交或拒绝进入 S'
```

如果没有状态转移契约，action 就会退化为堆叠事件。agent 可以做很多事，但系统无法可靠判断哪些行动改变了任务，哪些只是探索，哪些失败，哪些创造了义务，哪些应被忽略。

## 5. 状态转移契约

一个可用的 SGAR 转移至少应包含：

| 字段 | 问题 |
|---|---|
| `state_id` | agent 当前处在哪个被承认的状态？ |
| `preconditions` | 行动可执行前必须满足什么？ |
| `action` | 当前尝试的操作是什么？ |
| `observation` | 工具、环境、人或工件返回了什么？ |
| `verification` | 哪些证据决定行动是否成功？ |
| `transition_rule` | 验证通过后允许发生哪个状态改变？ |
| `commit_record` | 实际承认了什么，何时承认？ |
| `rollback_or_retry` | 验证失败或不确定时怎么办？ |
| `provenance` | 哪些来源、日志、测试、工具或批准支持该转移？ |

最小模式是：

```text
S + A -> O -> V -> S'
```

这就是硬状态治理的核心。把活动转化为进展的，不是 LLM 的自信或解释，而是状态转移。

## 6. 没有硬状态时的失败模式

### 6.1 状态漂移

状态漂移指 agent 的隐含位置在没有受治理转移的情况下发生变化。常见形式包括：

- 把计划当成已经完成的工作；
- 把猜测当成已经验证的证据；
- 把探索性结果当成最终结论；
- 忘记约束仍然有效；
- 在新证据推翻旧假设后仍继续沿用旧假设。

更长上下文并不能自动解决这个问题——更多历史反而意味着更多可被重新解释的材料。

### 6.2 状态振荡

状态振荡指 agent 因缺少外部锚点，在解释、阶段或优先级之间反复切换。它看起来一直在行动，实际上却在不断重新发现自己在哪里。

硬状态给系统一个稳定任务骨架。agent 不必每次从 transcript 中推断自己是谁、在哪里、已经承认什么。它读取当前治理状态，并在这个状态中行动。

### 6.3 表演性行动

如果 action 没有被状态吸收，它就会退化为表演。工具调用、计划、总结、审计和解释都可能看起来像工作，但系统无法判断它们是否真的改变了被承认的任务状态。

SGAR 要求 action 必须通过状态转移被解释。如果没有可提交转移，行动应被记录为探索、失败尝试、阻塞尝试或无关活动，而不是默默算作进展。

### 6.4 角色混淆

当 LLM 同时扮演操作者和最终验收者时，它容易接受自己编织的进展叙事。SGAR 把最终状态裁决权从生成行动的同一上下文中移出。

## 7. 研究型 Agent 更需要 SGAR

研究型任务尤其需要 SGAR，因为不确定性不是研究的暂时缺陷，而是研究本身。

研究型 agent 必须治理：

- 当前假设；
- 证据等级；
- 已验证结论；
- 未验证猜测；
- 已失败路线；
- 放弃理由；
- 不确定结果；
- 待复现义务；
- 争议点；
- 下一步研究义务。

没有硬状态，研究型 agent 很容易忘记已失败路线，把弱证据升级成强结论，把假设当事实，重复做相似实验，忽略负结果，或为了维持叙事连续而过度合理化。

SGAR 不是把研究机械化。它让不确定性被治理，而不是被遗忘。

## 8. 因果可读性，而不是真正因果保证

SGAR 不应被表述成能够保证"真正因果"。硬状态记录仍可能不完整、设计有误、观测不足，或绑定了有误导性的验证器。

更稳妥、也更有力的说法是：

> SGAR 为任务进展建立因果可读性。

这意味着系统可以检查如下链条：

```text
被承认的状态 -> 行动 -> 观测 -> 验证 -> 下一个被承认的状态
```

并追问：

- 哪个 action 声称改变了状态？
- 它产生了什么证据？
- 哪个验证器接受或拒绝了这个转移？
- 哪些承诺或义务发生了变化？
- 这条链能否复盘、审计、回滚或争议？

这是一种操作层面的因果，或者说受治理的因果。它不证明世界完整的外部因果结构，但为 agent 在任务中提供了可追踪的因果位置。

## 9. 条件性的可靠性主张

SGAR 也不应被说成"让预测天然更可靠"。更准确的说法是：当状态层设计良好时，SGAR 能够提高下一步行动选择的条件可靠性。

这种可靠性提升取决于：

- 状态变量保留了任务关键区别；
- 转移规则匹配真实工作流；
- 观测和验证通道捕捉了决定性证据；
- LLM 能正确读取硬状态；
- 过期状态会被撤销；
- 失败和负证据会被记录；
- 长程进展通过有效转移被承认。

当这些条件成立时，SGAR 能减少因定位错误造成的不确定性，agent 会在更清楚的操作场景中选择下一步。反过来，如果状态 schema 设计错误，SGAR 也可能把错误抽象制度化。因此硬状态虽然强大，但它本身也必须被治理。

## 10. 与现有框架的关系

### 状态失配

状态失配问的是：在当前观测通道下，我们处在哪个潜在状态？SGAR 并不是第七类原始失配，而是一套用于表示、更新、验证和恢复任务状态的 agent 治理体制。

### 观测-表征失配

观测-表征失配问的是：决定性变量是否进入了模型可访问的表征。SGAR 依赖这一点——如果变量从未进入观测、证据、工具、日志、传感器或编码控制表示，硬状态层也无法治理它。

### 知识治理与 GKO

知识治理管理任务特定知识。GKO 保存已验证的主张、条件、优先级、强度、生命周期、冲突和撤销规则。SGAR 为 agent 运行提供更广义的状态权威层，GKO 可以在其中被读取、应用、更新或撤销，并成为状态转移的一部分。

### GEO 与治理式协作

GEO 治理的是升级机制：什么时候该问、问谁、问什么、等待期间能做什么。在 SGAR 中，人类回答不应消失在聊天里，而应更新一个被承认的状态、GKO、GEO、义务或转移记录。

### 审计工程

审计工程把失败信号转化为控制增量。SGAR 提供吸收这些增量的状态基底：缺陷不只是被记录，而是改变被承认的状态、允许的行动、验证要求、回归义务或回滚条件。

## 11. 评估问题

SGAR 可以通过这些指标评估：

- **状态漂移率：** agent 的隐含状态多常偏离被承认状态；
- **虚假完成率：** LLM 多常在没有有效转移时宣称完成；
- **转移有效性：** 已提交转移多常满足证据和验证要求；
- **恢复成功率：** 中断后 agent 能否仅凭硬状态恢复；
- **可复盘性：** 另一个 agent 或审查者能否重建系统为何处于当前状态；
- **回滚质量：** 失败或撤销的转移是否会污染后续工作；
- **行动吸收质量：** 重要行动是否被正确归类为进展、探索、失败或阻塞；
- **可审计性：** 承诺、证据、验证器和责任人能否被检查。

## 12. 设计原则

1. **状态权威必须外置于单次推理。** 上下文摘要可以描述状态，但不应成为唯一权威。
2. **状态转移必须依赖验证。** "我完成了"必须变成"系统因证据通过门槛而承认完成"。
3. **计划不是状态。** 计划可以指导行动，但不能认证进展。
4. **记忆是辅助性的。** memory 支持认知，但不决定治理意义上的当前事实。
5. **负结果是一等对象。** 失败路线、不确定测试和撤销假设都应进入状态。
6. **人类输入应更新状态，而不只是进入聊天。** 人类判断应变成治理变量、批准、约束或撤销规则。
7. **硬状态必须可修订。** 重点是受治理的改变，而不是不可变。

## 结论

SGAR 是 agent 的状态治理层。它让 LLM 不再漂浮在自我维持的叙事中，而是在被承认的操作场景中行动。

最短命题是：

> 没有硬状态，agent 只有连续输出；有了硬状态，agent 才可能拥有连续行动。

对于任何需要长期运行、真实行动、失败恢复、承诺遵守、验收验证、人机或多 agent 协作，以及从自身轨迹中学习的 agent 来说，硬状态治理不是可选增强，而是系统真正成为 agent 的基础条件之一。
