# 从固定流程到受治理委托：新旧软件设计的根本区别

> English version: [From Fixed Workflows to Governed Delegation](from-fixed-workflows-to-governed-delegation.md)

生成式模型进入软件之后，最容易得到的解释是“软件变得更智能了”。这个说法没有错，却没有抓住设计变化的核心。真正发生变化的，不只是某个函数开始用自然语言，也不是固定流程中增加了一个模型节点，而是软件向上暴露的抽象单位正在扩大：

```text
函数 → 服务 → 流程 → 能力 → 领域责任 → 主体委托
```

传统软件主要由开发者预先枚举合法路径；新一代软件则开始允许系统在运行时根据任务残差、可信状态、预算、权限和验证结果选择下一步。前者设计“怎样执行一条已知路径”，后者设计“怎样在边界内决定路径，并证明结果可以被接受”。

这里的“新”与“旧”描述的是两种**控制权配置**，不是时间标签，也不等同于“使用 AI”与“不使用 AI”。规则引擎、搜索算法和自适应控制早已包含运行时决策；今天的新变化，是生成式模型把可运行时决定的范围从参数和分支扩大到了任务分解、能力选择与语义修复。现实系统通常位于连续谱上：一部分路径固定，另一部分决策开放。

这不是新旧软件的简单替换关系。可靠的新系统必须把自适应能力**挂载**在旧软件已经擅长的确定性基础上。越向上开放决策，越需要向下复用确定性能力，并在每个挂载点保留契约、证据和状态提交权。

本文只讨论这种变化对软件设计的影响，不试图把它扩展成一套完整的软件工程方法论。

> **项目语境说明：** 下文的六层责任模型是一种架构分类，不是本项目的[六类原始失配](six-primitive-mismatches-pipeline-derived-taxonomy-llm-systems.zh-CN.md)。受治理的自适应编排描述运行时决策权如何分配；[状态治理智能体范式（SGAR）](state-governed-agent-regime-for-governed-llm-systems.zh-CN.md)则提供接纳并提交这些决策所需的硬状态运行纪律。

## 一、旧设计枚举路径，新设计约束决策

在固定工作流中，开发者通常预先定义：

- 节点及其依赖；
- 条件分支；
- 重试与回退；
- Gate 与完成条件；
- 哪个状态可以提交。

运行时的主要职责，是在预定义图中执行和选择。即使工作流包含大量分支，它仍然属于“合法路径已基本枚举”的设计。

自适应系统不同。开发者无法也不应预先列出所有合理路径。运行时需要依据当前任务残差生成下一段任务图：调用哪项能力、读取什么上下文、修改哪些对象、如何验证，以及失败后应该修复、重规划、回滚还是升级给人。

因此，新旧设计的关键分界不在于是否使用大模型，而在于：

> **有多少执行路径的决定权被保留在设计期，又有多少被有条件地移交到运行期。**

一个通过 API 调用大模型、但路径和接受条件全部固定的系统，仍然是固定工作流。一个运行时可以重规划、却没有权限边界、验证器和状态提交规则的系统，也不能因此成为更高阶架构；它只是把不确定性传播到了系统状态。

可以把两种设计的中心问题压缩为：

| 设计范式 | 主要设计对象 | 运行时问题 | 主要风险 |
| --- | --- | --- | --- |
| 固定流程 | 已知路径与分支 | 当前处于哪个节点 | 漏掉预期分支 |
| 受治理的自适应编排 | 能力、状态、权限、证据和 Gate | 当前残差应委托给哪项能力 | 错误规划污染真实状态 |

旧设计优化路径；新设计治理决策。

## 二、六层不是智能等级，而是责任半径

把软件分成六层有助于识别变化，但这些层级不能按“模型越来越强”理解。更稳定的划分标准是：系统向上一层承诺了什么，以及它承担了多大的语义责任。

| 层级 | 向上暴露的抽象 | 核心承诺 | 完成语义 |
| --- | --- | --- | --- |
| L1 确定性工具 | 函数、命令、算子 | 完成一次明确变换 | 输出满足函数契约 |
| L2 网络化服务 | API、资源契约 | 跨执行域提供资源 | 请求满足服务契约 |
| L3 固定工作流 | 静态 DAG | 按已知流程交付结果 | 流程到达成功终态 |
| L4 自适应编排 | 受治理的动态任务图 | 为任务残差选择路径 | 路径结果经验证，由此产生的状态转移被提交 |
| L5 领域能力系统 | 专业能力契约 | 对一类专业结果负责 | 结果、证据和领域状态可交付 |
| L6 主体委托系统 | 人或角色的委托接口 | 为主体目标分配责任 | 目标被推进且未越权 |

这里包含三次性质不同的边界变化：

1. L1—L2 改变资源边界：能力在哪里运行、由谁提供。
2. L3—L4 改变控制边界：路径由开发者预定义，还是在运行时产生。
3. L5—L6 改变责任边界：系统为一个专业领域负责，还是代表某个主体协调多个领域。

层级由责任半径决定，不由代码量、组件数或模型参数量决定。一个使用强模型的 API 仍可能只是 L2；一个模型较弱但能维护主体状态、约束跨领域授权并正确升级的系统，可能承担 L6 的责任。

## 三、“挂载”是新旧设计之间最重要的关系

“从固定 DAG 升级为 Agent”容易让人误以为旧结构应被删除。更准确的设计动作是**挂载**：上层不复制或绕过下层，而是通过明确的挂载点调用下层已经成立的能力。

这里的“挂载”不是文件系统 mount，也不只是把工具名注册进插件目录。它表示：**上层把下层的一项能力纳入自己的责任结构，但不接管其内部实现，也不放弃本层的验收责任。**

一个有效的挂载点至少包含：

```text
能力标识
+ 适用范围与前置状态
+ 输入、输出与版本
+ 允许读取和写入的对象
+ 所需权限与预算
+ 成功证据与验证器
+ 超时、失败和回退语义
+ 可提交的状态变化
```

挂载点必须回答四个所有权问题：

| 问题 | 必须明确的所有者 |
| --- | --- |
| 谁可以发起调用 | 调用权限所有者 |
| 谁负责下层能力契约并提供其正确性证据 | 下层能力所有者 |
| 谁判断结果满足上层目标 | 上层验证或接受者 |
| 谁能把结果写入权威状态 | 状态提交权所有者 |

如果这四项没有分开，所谓挂载往往只是把一个不透明工具接到 Agent 后面：上层不知道下层承诺什么，下层也不知道哪些输出会触发真实状态变化。

因此，静态 DAG 不会因为出现动态编排而过时。已经验证过的转码管线、发布流程、账务结算或数据库迁移，应该作为原子能力挂载到自适应层。规划器可以决定“是否调用”和“何时调用”，但不应随意改写这些流程内部已经证明有效的不变量。

挂载还意味着上下行是非对称的：

```text
向下：目标 → 任务 → 委托 → 工作流 → 服务 → 函数
向上：结果 + 证据 + 成本 + 风险 + 来源 + 状态变化建议
```

向下传递的是被约束的执行权，向上传递的是可验证的交付物。下层返回成功，只证明下层契约得到满足，不自动证明上层目标已经完成。例如，API 成功返回一份法律分析，只说明服务调用成功；它不能证明分析适用于当前管辖区，更不能自动授权签署合同。

当上下层的完成语义不同，且结果可能进入持久、共享或高代价状态时，可以得到一个严格的设计原则：

> **跨层返回值只能成为上层的候选证据，不能越过上层 Gate 直接成为真实状态。**

如果上下层契约完全等价，上层当然可以把下层验证器组合进自己的 Gate；这仍然是显式继承验证，而不是因为“调用成功”就默认目标完成。

## 四、新设计的核心对象从控制流变成可提交状态

固定流程常以控制流为中心：节点是否成功、下一条边是什么、流程是否到达终点。自适应系统如果仍只维护这些信息，很容易出现状态跳跃：局部步骤失败后回到错误阶段，修复了候选却丢失其来源，或者把模型声称的“完成”误当作真实完成。

受治理的自适应系统至少要区分四类状态：

- **工作状态**：当前计划、活动节点、尝试次数和预算消耗；
- **产物状态**：候选版本、来源、父版本、修改范围和内容哈希；
- **评价状态**：硬约束、软债务、证据、评分和未解决风险；
- **提交状态**：哪个候选被谁、依据什么 Gate 接受为当前有效版本。

规划器可以提出状态变化，执行器可以产生候选，评价器可以给出证据，但只有拥有提交权的组件才能更新权威状态。这种职责分离不是为了增加角色数量，而是避免同一个不确定组件同时“采取行动、解释结果并宣布成功”。

所以，新设计中的状态转换更接近：

```text
可信状态 + 任务残差
→ 有界计划
→ 候选变化
→ 独立验证
→ 接受 / 修复 / 重规划 / 回滚 / 升级
→ 新的可信状态
```

任务图可以动态变化，权威状态的提交规则不能动态漂移。

## 五、Gate 必须区分硬约束与软判断

固定流程倾向于把所有检查写成布尔条件。这在条件稳定、结果可精确判断时有效，但用于开放任务会导致两个极端：要么把所有质量偏好硬编码，系统反复迭代而不能停止；要么把决定完全交给模型，硬约束也被高总分抵消。

更合理的 Gate 由两部分组成：

### 不可补偿的硬 Gate

- schema、类型和结构有效；
- 权限、写入范围和数据边界未被突破；
- 明确声明的硬约束逐条得到证据支持；
- lineage、版本和来源闭合；
- 没有未恢复的失败或阻断级风险；
- 必需产物存在且可读取。

硬 Gate 失败时，总分、成本或主观评价都不能补偿。

### 可权衡的软 Gate

- 风格和表达是否还有提升空间；
- 非关键缺口是否值得继续修复；
- 预期增益是否高于修改成本与回归风险；
- 当前质量是否足以支持下游阶段。

软 Gate 可以由 Agent 判断，但判断必须持久化理由、剩余风险和证据。所谓“灵活”不是取消 Gate，而是把不可协商条件与可权衡债务分开。

这也为迭代停止提供了清晰依据：达到硬 Gate 后，如果候选质量已满足目标，且继续修改的预期收益低于成本或回归风险，系统应进入下一阶段，而不是为了耗尽轮数继续生成。

## 六、什么时候应该使用固定流程，什么时候需要 Agent

新设计的价值不是让所有任务动态化，而是把不确定性放在确实需要决策的地方。

可以用两个问题做第一轮判断：

1. 合法执行路径能否在设计期基本枚举？
2. 结果是否能由稳定的确定性或结构化 Gate 判断？

| 路径 | 验收 | 更合适的设计 |
| --- | --- | --- |
| 可枚举 | 稳定 | 固定 DAG |
| 可枚举 | 需要语义判断 | 固定 DAG + 语义评价器 |
| 不可枚举 | 稳定 | 动态规划 + 确定性 Gate |
| 不可枚举 | 需要语义判断 | 受治理的自适应编排 + 独立复审/升级 |

只有当系统需要长期维护领域对象、政策、证据和失败分类时，才有必要上升到领域能力系统。只有当它还必须代表一个主体处理跨领域目标、权限冲突、预算和长期承诺时，才有理由引入主体委托层。

不要为了使用 Agent 而制造动态性。路径越固定，越应该把它固化为可复用能力；判断越开放，越应该加强证据、权限和升级机制。

### 一个具体对照：短视频交付

假设系统需要把一批素材制作成可发布的短视频。

旧式固定流程可以是：读取媒体信息、统一转码、响度标准化、叠加指定字幕、抽样检查、导出。只要输入格式和发布标准稳定，这条 DAG 简单、便宜且可复现，没有理由让 Agent 逐步重新规划。

当任务改为“从访谈素材中制作三种受众版本，保留关键论点，避免断章取义，并在总时长限制内选择节奏”时，完整路径难以预先枚举。系统需要判断素材相关性、选择片段、发现证据不足并补读上下文，可能还要在质量和时长之间重规划。这里适合开放 L4 决策。

但开放的只是**编辑决策**，不是全部执行：

```text
Agent 选择片段与版本策略
→ 挂载“素材定位与时间码提取”能力
→ 挂载“已验证转码与响度处理”DAG
→ 生成候选视频与引用清单
→ 独立检查语义完整性、版权、时长和发布规格
→ 通过 Gate 后提交发布版本
```

如果转码失败，应从转码节点恢复；如果语义检查失败，应回到片段选择或局部编辑；二者都不应无理由回到“重新理解全部素材”。这个例子显示了状态分层和挂载的直接收益：动态层减少无效固定路径，固定层避免重复发明可靠执行，Gate 防止局部成功冒充整体完成。

## 七、从旧系统演进到新系统的设计路径

一种风险较低的演进方式，不是重写全部流程，而是逐层建立挂载点。

### 1. 固化确定性岛屿

识别已经稳定的函数、服务和流程，明确输入输出、错误、幂等性和版本。它们是自适应系统的执行地基，不是需要被 Agent 取代的遗留物。

### 2. 把流程封装为能力契约

不要让规划器直接操作零散工具。把一段可验证流程封装成带前置条件、授权范围、产物、证据和失败路由的能力。

能力契约还应声明兼容版本及撤载条件。替换实现时，上层依赖的是契约与证据格式，而不是供应商名称或某段提示词；无法满足新契约的旧能力应当被撤载，而不是继续隐式兼容。

### 3. 建立权威状态与候选状态

运行时修改首先进入候选状态。只有通过对应层级 Gate 后，候选才能提交为权威状态。恢复和重试必须从持久化状态继续，而不是依赖模型回忆当前阶段。

### 4. 只开放必要的决策点

让 Agent 决定真正不确定的部分，例如能力选择、局部修复策略或是否升级；固定已经确定的安全检查、事务边界和发布步骤。

### 5. 按风险分离生成权与验证权

生成结果必须携带可检查证据。低风险系统可以合并生成与验证角色，但当结果可能进入真实状态时，提议者不能成为验证自身成功的唯一权威。高风险场景需要独立验证器、复审 Agent 或人工接受者，且验证结果不能由生成者自行覆盖。

### 6. 从影子模式逐步取得提交权

先让系统提出计划和候选但不提交，对比其决策与既有流程；再按风险等级逐步开放写入范围。能力可以先挂载，权威状态的提交权应最后授予。

## 八、五个常见的设计误区

### 误区一：用了大模型就是新架构

模型是实现手段。架构层级取决于向上承担的责任和状态边界。

### 误区二：动态任务图应替代静态 DAG

动态层负责选择路径，静态 DAG 负责执行已知且验证过的路径。二者是挂载关系，不是替代关系。

### 误区三：Agent 可以同时规划、执行和验收

低风险探索可以合并角色；一旦结果会进入真实状态，行动权与接受权就应分离或受到外部 Gate 约束。

### 误区四：更多重试代表更强的自适应性

没有状态残差、失败分类和新证据的重试只是重复抽样。有效迭代必须解释上次为何失败、保留最佳已知候选，并把修复限定在授权范围内。

### 误区五：长期记忆等于领域状态

对话记录不是权威台账。领域状态需要对象模型、版本、来源、提交者、验证结果和可恢复的转换历史。

## 九、哪些结论是硬的，哪些仍是假设

对这套观点做严格审视后，可以把结论分为两类。

### 在本文适用范围内较硬的结论

这里的“硬”不是数学定理，而是针对**会修改持久、共享或高代价状态，且要求可审计与可恢复的软件**所提出的设计不变量。

1. **是否使用模型不能定义架构层级。** 同一模型可以被包装成函数、服务、工作流节点或规划器；分类必须依据向上契约和责任范围。
2. **运行时决策越开放，治理要求不能越弱。** 如果路径不能预先枚举，系统至少需要显式状态、权限边界、证据、Gate 和失败路由，否则无法可靠区分探索与提交；低风险、无持久副作用的沙箱探索不在此约束范围内。
3. **上层不能以成功返回替代本层验收。** 每层“完成”的语义不同，跨层结果必须在本层重新验证。
4. **确定性能力不会因 Agent 出现而失效。** 可枚举且稳定的流程仍应保持固定，并作为能力挂载到动态层。
5. **动态路径与权威状态必须解耦。** 计划可以变化，但真实状态只能通过稳定、可审计的提交协议变化。

这些结论不是对所有实现细节的唯一规定，但具有可检验性：如果一个系统绕过其中任何一条，就应能说明它用什么等价机制保证权限、证据、一致性和恢复，并用故障注入或审计记录证明该机制确实成立。

### 有指导价值但仍需验证的假设

1. 六层是有用的设计坐标，但不是所有产品都必须实现的成熟度阶梯。
2. “领域能力系统”可能成为复杂 Agent 产品的主要组织单元，但不同领域所需状态和验证结构差异很大。
3. 通用 Agent 更可能成为优秀的委托者而非全能执行者；这个方向合理，却仍取决于专业能力市场、互操作标准和责任制度是否成熟。
4. 动态编排可以降低固定 DAG 的无效开销，但只有在规划成本、验证成本和错误成本合计更低时才成立。

把预测写成结构事实，会让文章显得有力却无法指导设计。更有用的做法，是把不可违反的不变量与仍待实践验证的产品判断明确分开。

### 用于设计评审的五个问题

读完架构图后，可以用五个问题检验设计是否真正成立：

1. 哪些路径必须固定，哪些决策确有必要在运行时开放？
2. 每项下层能力通过什么契约挂载，四类所有权是否明确？
3. 候选状态与权威状态是否分离，谁拥有最终提交权？
4. 硬约束是否逐条、不可补偿地验证，软债务是否留下判断理由？
5. 任一节点失败后，系统能否从正确层级恢复，而不是无依据地回到起点？

如果这些问题没有具体答案，“Agent 化”通常只改变了调用方式，并没有形成可靠的新软件设计。

## 结语：新软件不是少设计，而是设计新的控制面

旧软件把大部分决策固化在代码和流程图中；新软件把一部分决策移动到运行时。移动决策不等于取消设计。设计工作的重点随之从“列出所有步骤”转向：定义能力边界、挂载关系、权威状态、证据标准、权限范围、停止条件和升级路径。

因此，新旧软件设计最准确的区别不是确定性与智能的对立，而是：

> **旧设计主要预定义执行路径；新设计主要约束运行时决策。**

一个稳定的新系统也不会是“一个通用 Agent 加很多工具”，而更像一组分层挂载的责任结构：

```text
主体委托
→ 领域能力
→ 受治理的自适应编排
→ 已验证的固定流程
→ 网络化服务
→ 确定性工具
```

上层向下委托，不能绕过权限；下层向上举证，不能自行宣布完成；动态路径可以改变，权威状态只能经 Gate 提交。只要这三个条件成立，Agent 才是在扩大软件能够承担的责任，而不是扩大不确定性的传播范围。
