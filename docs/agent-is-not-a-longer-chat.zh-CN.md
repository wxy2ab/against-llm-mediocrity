# Agent 不是更长的 Chat

## Chat、Bot 与 Agent 的任务权威为何根本不同

[English](./agent-is-not-a-longer-chat.md) · 中文 · [五轮审校记录](./agent-is-not-a-longer-chat.review.md)

> 面向构建或采购 Agent 系统的产品经理、应用工程师与平台工程师。本文讨论的不是产品命名，而是：当人类不再逐步盯住任务时，谁有权解释状态、执行副作用、接受证据和宣布完成。

很多所谓的 Agent 架构，本质上仍然是 Chat 架构的延长版：

* 给 Chat 增加工具调用；
* 给 Chat 增加循环；
* 给 Chat 增加长期记忆；
* 给 Chat 增加一个 planner；
* 再让模型自己判断是否完成任务。

这种系统可能比普通对话更复杂，却没有真正跨越从 Chat 到 Agent 的设计边界。

Chat、Bot 与 Agent 的差异，并不主要在于是否使用了大模型、是否调用工具、是否存在多轮循环，也不在于一次运行持续几秒还是几个小时。它们真正的区别是：

> **当任务持续推进时，谁拥有状态解释权、任务提交权、偏移纠正权、路线选择权和最终验收权。**

在 Chat 和大多数 Bot 中，这些权威主要掌握在人类手中。
在人类不再逐步干预的 Agent 中，这些原本由人类隐式承担的职能，必须由系统中的显式机制承接，例如外部运行时、状态治理层、路由策略、验证器、审计器和人工升级点。

因此，Chat、Bot 与 Agent 不只是同一种系统的三个复杂度等级，更是三种不同的**任务权威结构**。

本文用“权威”表示对任务事实具有提交效力的权限，而不是一般意义上的影响力。LLM 可以强烈影响计划和候选结果；只有被授权的机制，才能把候选写成任务事实。对于低风险、可逆、易验证的任务，这套机制可以很轻；任务越长、越开放、越高风险，治理就应越显式。

### 一句话版本

> **Chat 依靠人类在每轮对话中维持任务真相；Agent 必须让运行时在没有逐轮监督时仍能区分提案、观察、证据和已提交事实。**

---

## 一、先限定这里所说的 Chat、Bot 与 Agent

为了避免概念争论，本文不按照产品名称区分三者，而按照运行时的控制关系区分。

### 1. Chat：人类逐轮参与的协作系统

Chat 的基本结构是：

```text
人类提出请求
→ LLM 生成响应
→ 人类阅读、判断、补充、纠正
→ LLM 再次响应
```

在这个结构中，人类始终位于循环内部。

人类知道自己真正想解决什么，知道哪些信息已经改变，知道模型是否误解了问题，也知道什么时候应该换一种方法。即使这些信息没有完整写进对话，人类仍然在头脑中维护着一个远比上下文窗口更完整的任务状态。

因此，Chat 的真实控制结构并不是：

```text
LLM 独立解决任务
```

而是：

```text
人类控制任务
LLM 提供认知劳动
```

LLM 可以犯错，因为人类会发现；LLM 可以遗漏状态，因为人类记得；LLM 可以误判完成，因为人类不会因此自动提交结果。

Chat 的可靠性，在很大程度上来自一个经常没有被计入系统架构的组件：**持续在线的人类控制面**。

---

### 2. Bot：边界明确、仍由人类监督的局部委托系统

这里的 Bot，是指承担一个相对固定角色、处理有限任务、由人类启动或监督的系统。

例如：

* 客服机器人回答常见问题；
* 编程机器人生成一段代码；
* 邮件机器人起草回复；
* 数据分析机器人生成报表；
* 工作流机器人执行一个有限流程。

Bot 可能比 Chat 更结构化，也可能有工具、规则、数据库和短期状态，但通常仍具有以下特征：

1. 任务边界相对固定；
2. 单次任务持续时间有限；
3. 结果容易被人类检查；
4. 人类可以随时中断、重启或覆盖；
5. 最终结果通常仍由人类接受或拒绝。

所以 Bot 与 Chat 的界面可能不同，但权威结构仍然类似：**人类仍然是任务状态和最终正确性的权威来源。**

一旦某个 Bot 开始在长时间内无人监督地推进开放任务，自主改变计划、调用不同能力、修改环境，并自行决定是否完成，它在功能上就已经进入了 Agent 范畴。

---

### 3. Agent：人类退出逐步控制循环后的持续委托系统

Agent 的核心不是“会调用工具”，而是：

> **人类把一个具有持续时间、状态变化和中间不确定性的任务委托给系统，并在一段执行过程中不再逐步决定每一个动作。**

其基本结构变成：

```text
人类提交任务
→ Agent 长程运行
→ Agent 自主维护任务进展
→ Agent 自主选择能力与路线
→ Agent 自主验证和纠偏
→ Agent 提交最终结果
```

“不再逐步参与”不等于人类永远退出。人在审批、风险接受、需求冲突或系统无法验证时仍可重新进入；关键是系统不能依赖人类在每一步替它维护状态和纠偏。

此时，人类不再逐轮承担以下职责：

* 记住任务已经进行到哪里；
* 判断哪些结论已经成立；
* 发现当前路线已经偏离目标；
* 决定是继续、回退、修复还是换路；
* 判断一个阶段是否真正完成；
* 区分模型的设想、计划、描述和已经发生的事实。

这些职责不会因为人类离开循环而消失。

如果 Agent 架构没有显式承接它们，它们就会被默认交给 LLM。而 LLM 恰恰不适合成为这些权威的最终承担者。

这就是 Chat/Bot 与 Agent 的根本分界。

---

## 二、Chat 和 Bot 中，人类才是真正的状态机

在普通对话中，人们常常认为“上下文窗口就是状态”。这并不准确。

上下文只包含被表达出来的文本。真正的任务状态往往存在于人类头脑中。

假设一个用户正在通过 Chat 修改一篇论文。对话中可能没有完整记录以下内容：

* 用户真正想保留的中心论点；
* 哪些修改只是探索，尚未接受；
* 哪个版本是当前权威版本；
* 哪些审稿意见已经处理；
* 哪些结论证据不足；
* 哪些段落只是临时占位；
* 用户对风险、篇幅和投稿方向的隐含权衡。

但是用户知道这些。

模型改错了，用户会指出；模型忘记了前文，用户会补充；模型把一个暂定方案当成最终方案，用户会纠正；模型说“已经完成”，用户会自行检查。

因此，Chat 中存在一个隐式状态转换：

$$
S_t^H
\xrightarrow{\text{LLM 输出}}
P_t
\xrightarrow{\text{人类判断}}
S_{t+1}^H
$$

其中：

* $S_t^H$ 是人类维护的真实任务状态；
* $P_t$ 是模型提出的候选响应；
* 人类决定是否接受、修改、拒绝或重新提问；
* 只有经过人类判断，模型输出才可能转化为任务进展。

LLM 输出在这里是一种**提案**，不是自动成立的事实。

---

### Chat 中的人类同时承担了五个隐式角色

#### 1. 状态维护者

人类知道任务当前处于什么阶段，哪些约束仍然有效，哪些信息已经过期。

#### 2. 任务审计者

人类会判断模型是否误解要求、是否遗漏关键内容、是否虚构事实、是否偏离目标。

#### 3. 偏移纠正者

模型开始讨论无关内容时，人类会说“不是这个意思”“回到前面的问题”“不要扩展这个方向”。

#### 4. 路由控制者

人类决定下一步应该继续追问、要求搜索、要求写代码、上传文件、换模型还是结束任务。

#### 5. 最终提交者

模型说“完成”没有决定性意义。人类接受结果，任务才真正结束。

这些职能在 Chat 界面里通常不可见，却构成了 Chat 能够稳定工作的基础。

---

### 因此，Chat 没有必要取得任务主权

Chat 可以维护会话记录，可以记住用户偏好，也可以增加一些安全检查。但试图让 Chat 自己取得完整的任务状态权威、审计权威和完成权威，在根本上没有太大意义。

因为人类始终在场。

这不是说 Chat 不需要任何状态机制，而是说：

> **Chat 中的状态机制主要服务于便利性、连续性和个性化，而不是替代人类成为任务真相的最终权威。**

在 Chat 中，即使系统状态不完整，人类也能够补齐；即使模型对状态做了错误解释，人类也能够覆盖；即使系统没有严格的任务状态机，人类也能够通过自然语言继续推进。

因此，Chat 可以是模型中心的。

## 三、为什么 LLM 可以成为 Chat 和 Bot 的中心对象

这里的“中心对象”不是严格的编程语言术语，而是一个架构判断：系统的主要接口、生命周期和其他组件是否都围绕模型调用组织。

典型的 Chat 架构是：

```text
Conversation
 ├─ messages
 ├─ model
 ├─ system prompt
 ├─ tools
 └─ memory
```

系统围绕一次次模型调用组织：

```text
组装上下文
→ 调用模型
→ 返回文本
→ 等待下一轮用户输入
```

在这种架构中，以 LLM 为中心是合理的。

原因不是 LLM 足够可靠，而是它不需要独自承担最终可靠性。

它可以：

* 根据当前上下文自由解释任务；
* 用自然语言表达不确定状态；
* 在不同轮次改变思路；
* 把计划、假设和结论混合在一次回复中；
* 依赖用户发现问题；
* 依赖用户决定哪些内容应被保留。

即使模型内部状态存在漂移，用户仍然是稳定锚点。

Bot 也可以在一定程度上保持模型中心。只要它的任务边界足够窄、失败容易被发现、结果不会自动产生高风险状态转移，围绕模型组织系统仍然是可接受的。

但这种结构不能自然延伸到长程 Agent。

---

## 四、Agent 不是把 Chat 循环运行更多次

一个常见误解是：

```text
Chat + 工具 + 记忆 + 循环 = Agent
```

这个公式缺少最重要的部分：**权威迁移**。

当人类退出循环后，仅仅增加更多模型调用，不会自动生成原本由人类承担的控制能力。

相反，Chat 中许多可以被人类轻易吸收的小问题，会在长程运行中累积成系统性故障。

例如：

### 目标漂移

模型每轮根据当前前缀重新解释任务。细微的重述不断积累，最终执行目标和原始任务已经不同。

### 状态震荡

模型在不同方案之间反复切换。上一轮认为 A 正确，下一轮根据新上下文又回到 B，但系统没有明确的提交和撤销机制。

### 虚假完成

模型生成了一段“我们已经完成了 X”的描述，运行时便把这段语言当成事实，尽管对应产物没有生成、测试没有通过、外部环境也没有改变。

### 记忆污染

未经验证的假设、过期信息、失败方案和真实结论以相同形式写入 memory。后续检索时，它们被无差别重新放入上下文。

### 自我确认

同一个模型提出方案、解释方案、评价方案，并根据自己的评价宣布完成。生成过程的盲区被原样传递到审计过程。

### 路由坍缩

无论任务属于确定性执行、开放探索、语义判断、硬验证还是异常恢复，系统都把它重新包装成一次 LLM 请求。

这些问题在 Chat 中可以由人类及时打断。
在 Agent 中，它们会沿着任务轨迹传播。

因此，Agent 的问题不是“怎样让模型连续工作更久”，而是：

> **怎样让一个不确定的认知组件，在没有人类逐步监督的情况下，仍然只能在受治理的任务环境中推进。**

## 五、Agent 中，LLM 不能成为最高任务权威

文章标题所说的“不是”，针对的是最高任务权威，而不是组件地位。LLM 当然可以是一等的、可组合的软件对象，也可以是系统里最重要的能力来源；问题在于，Agent 的顶层任务模型不能只围绕模型、对话或 prompt 组织。它还应把以下对象提升到一等地位：

* Mission；
* Task State；
* State Transition；
* Artifact；
* Evidence；
* Capability；
* Verification；
* Commitment。

LLM 仍然可以非常重要，甚至决定系统能够找到多高质量的候选解，但它不应仅凭自身声明获得任务状态的最终解释权和权威写入权。

Agent 的核心结构应当更接近：

$$
C_t = R(S_t)
$$

$$
A_t^{proposal} = M(C_t)
$$

$$
O_t = E(S_t, A_t^{proposal})
$$

$$
D_t = V(S_t, A_t^{proposal}, O_t)
$$

$$
S_{t+1} = Commit(S_t, A_t^{proposal}, O_t, D_t)
$$

其中：

* $S_t$ 是由 LLM 之外的运行时维护的权威任务状态；
* $R$ 根据任务状态渲染当前上下文；
* $M$ 是 LLM，负责提出候选动作；
* $E$ 是执行环境；
* $O_t$ 是通过工具或传感器取得的观察结果；
* $V$ 是验证或审计机制，$D_t$ 是其判定；
* `Commit` 决定结果是否能够成为新的权威状态。

最关键的限制是：

> **LLM 可以提出状态变更，但不能仅凭自己的自然语言声明直接修改权威状态。**

这并不禁止 LLM 直接编辑草稿、工作区或其他可逆对象。关键区分是“产生副作用”和“提交权威事实”：低风险写入可以预先授权，高风险写入应经过审批；无论哪一种，产物都不应仅因模型说“完成了”就被标记为已验证。

模型可以说“代码已经修复”，但只有测试、检查和提交机制通过后，任务状态才能从“修复中”转移到“已修复”。

模型可以说“这一阶段已经完成”，但只有退出条件满足并经过验证，阶段才能关闭。

模型可以提出“应该换一条路线”，但是否允许换路，应由路由策略、预算、风险和当前任务状态共同决定。

这不是削弱模型，而是把模型放到它最适合的位置上：

> **LLM 负责生成、解释、推断、规划和提出候选；外部机制负责定义什么能够成为任务事实。**

## 六、Agent Harness 的根本意义：用外部规则约束内部不确定性

Agent harness 经常被理解为：

* 工具封装；
* prompt 模板；
* 模型调用接口；
* planner；
* 重试循环；
* 多 Agent 编排器。

这些都可能是 harness 的组成部分，但都不是它的根本意义。

对于需要长程可靠性的系统，Agent harness 的核心作用是：

> **在概率性的模型认知之外，建立一个具有明确规则、稳定语义和可验证状态转移的任务制度。**

这里的“外部规则”不意味着外部代码能够自动知道所有开放问题的真相。确定性代码无法替代模型完成复杂语义判断，也无法凭空解决未知问题；观察本身还可能不完整，验证器也可能写错。

它提供的是另一种确定性：

* 哪个状态是当前权威状态；
* 哪些信息只是候选；
* 哪些结果已经通过验证；
* 哪些动作在当前状态下合法；
* 哪些条件满足后才能提交；
* 哪些失败必须导致回退；
* 哪个组件有权修改哪类状态；
* 哪些中间结果必须保留证据；
* 什么时候必须停止、升级或请求人类介入。

这是一种**规则与提交语义的确定性**，而不是内容真理的确定性。它降低的是未经检查的候选被当成事实的概率，不保证所有被提交的结论都正确。

LLM 的不确定性无法被完全消除，但可以被限制在候选生成、语义分析和受控决策范围内。它不再能够把一次自信的语言生成直接升级为系统事实。

因此，好的 Agent harness 不是让 LLM “更像一个自主的人”，而是防止整个系统把 LLM 的语言表现误认为任务现实。

## 七、Agent 必须维护的是任务状态，而不仅是执行状态

很多 Agent 系统声称自己“有状态”，实际上只维护了执行状态。

例如：

```text
当前运行到第几个节点
工具调用是否返回
重试了几次
哪个进程正在运行
哪些文件被创建
当前使用哪个模型
```

这些信息当然重要，但它们主要回答：

> 系统现在正在做什么？

它们不能完整回答：

> 当前任务已经成立了什么？哪些结论可以被信任？哪些目标尚未达成？下一步为什么合法？

这两类状态必须区分。

| 执行状态     | 任务状态         |
| -------- | ------------ |
| 当前运行节点   | 当前任务阶段       |
| 工具调用 ID  | 已接受的任务目标     |
| 进程是否退出   | 已验证的任务进展     |
| 重试次数     | 尚未解决的约束      |
| 文件是否存在   | 哪个文件是权威产物    |
| 当前模型     | 当前能力需求       |
| DAG 节点完成 | 阶段退出条件是否满足   |
| API 返回内容 | 返回内容是否成为有效证据 |

一个工作流节点完成，不等于任务取得进展。

一个文件被写入，不等于文件满足要求。

一次测试运行结束，不等于测试通过。

模型完成一轮推理，更不等于某个任务状态发生了合法转移。

---

### 任务状态是什么

任务状态至少包含以下语义：

* 当前有效目标；
* 任务边界与约束；
* 已接受的事实；
* 尚未验证的假设；
* 已提交的决策；
* 当前权威产物；
* 已完成和未完成的阶段；
* 阶段退出条件；
* 未解决问题；
* 风险与阻塞；
* 能力需求；
* 可执行的合法动作；
* 当前状态的证据来源；
* 状态变更的提交记录。

这些内容不是一段摘要文本，而是一个具有类型、权限和转移规则的任务模型。

---

### 状态赋予 Action 意义

在缺少明确任务状态的系统中，很多所谓 action 只是语言姿态：

```text
继续
重试
修复
重新规划
回退
验证
完成
```

如果这些动作不对应真实的状态转移，它们就没有稳定语义。

“重试”到底是在相同输入上重复调用，还是换模型、换方法、恢复检查点？

“修复”针对的是代码错误、规格错误、数据错误，还是任务路线错误？

“完成”是模型认为没有更多内容可写，还是退出条件已经全部满足？

“回退”是撤销一个文件、一个阶段、一个决策，还是仅仅在上下文中说“我们重新开始”？

只有在明确状态下，action 才能获得确定含义：

$$
S_t + A_t \rightarrow O_t \rightarrow V_t \rightarrow S_{t+1}
$$

动作不一定修改环境：读取、诊断和请求审批都可以是合法动作。但它至少应产生可追踪的观察、证据、授权请求或状态转移。否则，“执行了”“验证了”“完成了”就只是模型对动作的描述。

---

## 八、为什么 Memory 不足以成为 Agent 的中心抽象

Memory 是当前 Agent 讨论中最容易造成混淆的概念之一。问题不在于使用 memory，而在于把它当成状态、权限、证据和产物治理的总称。

它把大量性质完全不同的信息统一视为“可以保存和检索的内容”：

* 用户信息；
* 环境信息；
* 任务信息；
* 会话信息；
* 历史计划；
* 模型假设；
* 工具返回；
* 中间结论；
* 失败记录；
* 最终产物。

在 memory 系统中，这些内容通常被统一表示成：

```text
一段字符串
+ 时间戳
+ 标签
+ embedding
+ 相似度
```

这种抽象对 Chat 很有用。

Chat 的主要问题是：怎样在下一轮对话中，让模型看到可能相关的历史内容。Memory 因而是一个围绕**内容连续性**设计的机制。

但 Agent 的主要问题不是“还能不能想起一段内容”，而是：

* 这段内容属于什么语义类型？
* 它是否仍然有效？
* 它来自谁？
* 它是否经过验证？
* 它是否有权影响当前任务状态？
* 它能否触发状态转移？
* 它与当前权威产物是什么关系？
* 它过期后应当被撤销、归档还是继续保留？
* 它是事实、观察、假设、偏好、计划还是决策？

Memory 无法仅凭“保存并检索了内容”回答这些问题。

---

### Memory 解决存取问题，Agent 还需要治理分类

这一区分可以概括为：

> **Memory 是一种存取范畴；状态是一种治理范畴。**

例如，下面几句话在 memory 中都可能只是普通文本：

```text
用户偏好使用 Python。
当前 API 返回 429。
实现已经完成。
测试尚未通过。
下一个阶段需要重构路由。
用户允许修改生产环境。
```

但在 Agent 中，它们必须进入完全不同的机制。

#### “用户偏好使用 Python”

它属于用户偏好和交互策略，可能影响方案选择，但未必是硬约束。

#### “当前 API 返回 429”

它属于带时间戳的环境观察，可能很快过期，并触发退避或切换服务。

#### “实现已经完成”

它只是一个完成声明。在验证前，不应进入已完成状态。

#### “测试尚未通过”

它属于任务阻塞和验证结果，应当禁止阶段提交。

#### “下一个阶段需要重构路由”

它可能是规划提案，不是已经提交的任务决策。

#### “用户允许修改生产环境”

它属于权限和风险控制，必须具有明确作用域、时限和撤销机制，不能依赖语义相似度检索。

这些内容即使都能被 memory 保存，也不能被 memory 以相同方式治理。

---

### Agent 中至少应区分五类机制

#### 1. 用户信息机制

维护用户身份、偏好、权限、长期目标和明确约束。

用户偏好与用户授权不能混在一起。
“喜欢简洁输出”和“允许删除生产数据”显然不能只是两条平级 memory。

#### 2. 环境信息机制

维护当前可观察环境、资源、工具能力、外部系统状态、数据版本和时间敏感信息。

环境信息必须强调时间、来源和可刷新性。

#### 3. 任务状态机制

维护任务目标、阶段、约束、已提交决策、验证结果、未解决问题和退出条件。

这是 Agent 的核心权威状态。

#### 4. Session 信息机制

维护本次运行所需的临时上下文、当前工作集和短期交互记录。

Session 可以丢弃、压缩和重建，不应成为任务事实的唯一来源。

#### 5. Evidence 与 Artifact 机制

维护证据、工具结果、测试报告、文件版本、产物关系和验证记录。

产物存在，不代表产物有效；证据必须与对应 claim、状态转移和验证规则关联。

因此，memory 可以作为某些机制的底层存储实现，但不能成为 Agent 的顶层理论模型。

把所有这些对象都称为 memory，就像把数据库中的订单、权限、审计日志、账户余额和临时缓存都称为“数据”，然后试图用一个统一的检索接口完成整个业务系统一样。它在存储层面没有错，在机制层面却几乎没有提供任何有效区分。

---

## 九、上下文不能成为 Agent 的唯一事实来源

Chat 系统通常把 conversation history 当成主要上下文。这在有人类监督时可以工作。

但在 Agent 中，不能把不断增长的上下文叙事当成唯一的任务权威状态。对短小、可逆、由人立即验收的任务，对话历史可能已经够用；问题出现在系统需要跨阶段恢复、并发协作、执行高风险写入或自行验收时。

原因是自然语言上下文天然混合了：

* 已发生的事实；
* 模型提出的设想；
* 尚未验证的假设；
* 已经放弃的路线；
* 工具的原始返回；
* 模型对工具结果的解释；
* 阶段性总结；
* 修辞性的完成声明；
* 过期信息；
* 相互冲突的结论。

如果 Agent 每一步都从这段叙事中重新推断“现在进行到哪里”，状态就会随着上下文表述不断被重解释。

更合理的方向是：

> **关键上下文应当由权威状态渲染；如果需要从对话中恢复状态，恢复结果必须重新核对并提交。**

也就是：

```text
Task State
+ 当前相关 Artifact
+ 当前相关 Evidence
+ 当前 Capability Contract
→ 渲染本步 Context
→ LLM 提出候选动作
```

而不是：

```text
把所有历史消息重新塞给 LLM
→ 让 LLM 猜测当前任务状态
→ 让 LLM继续工作
```

这可以称为对上下文的降级：上下文仍然重要，但它只是 Agent 在某一时刻看到的工作视图，而不是任务真相本身。

---

## 十、异构任务需要状态感知的能力路由

长程任务不是一个同质问题。

同一个任务内部可能同时包含：

* 可以由静态代码确定完成的部分；
* 适合通过 API 调用外部服务的部分；
* 适合固定 DAG 执行的部分；
* 需要动态规划的部分；
* 需要专业模型或专业 Agent 的部分；
* 需要分离式审计的部分；
* 只能升级给人类处理的部分。

这些子任务的难度、风险、可验证性、状态依赖和适合能力都不相同。

对于这类异构任务，Agent 不能只是让同一个 LLM 在统一循环中不断选择“下一步做什么”。边界固定、能力单一的 Agent 可以使用固定路线，不必为了“像 Agent”而引入动态路由。

复杂 Agent 需要控制一种**异构能力路由**：根据当前权威状态，把不同问题路由给不同性质的能力和机制。原稿称它为“参差路由”，强调的正是任务难度和能力边界并不整齐。

例如：

```text
确定性转换
→ 静态函数

明确远程资源调用
→ 服务 API

步骤和验证边界已知
→ 静态 DAG

计划可变但治理边界明确
→ 动态 DAG

专业语义判断
→ 专业能力或专业 Agent

结果存在高风险或低可信
→ 分离式审计或人工审批

缺少可用验证边界
→ 暂停、硬化条件或升级人类
```

这里的关键不是“模型会不会挑工具”，而是系统有没有把不同能力的适用边界显式建模。

---

### 路由不能完全依赖 LLM 的自我判断

模型可以参与判断任务类型，可以提出路由建议，但不能仅凭一句“我认为应该使用 X”就获得无限制的行动权限。

真正的路由还需要考虑：

* 当前任务状态；
* 能力契约；
* 风险等级；
* 可用预算；
* 权限边界；
* 历史成功率；
* 验证能力；
* 当前是否存在阻塞或震荡；
* 该动作是否允许修改权威产物。

因此，Agent 中应当存在两个层次：

```text
LLM 提出认知上的路由建议
外部 runtime 决定是否提交该路由
```

动态执行并不意味着所有东西都动态化。

好的 Agent 应当保留一个相对稳定的治理骨架，例如任务阶段、状态提交、验证、权限和退出条件；在这个硬边界内，允许模型灵活调整搜索路线、能力组合和局部执行顺序。

也就是说：

> **执行路线可以柔性变化，治理边界不能随模型叙事一起漂移。**

---

## 十一、Agent 需要分离式审计，不能只靠编排器自我反思

在 Chat 中，人类天然承担审计职责。

人类会看到模型的结果与真实意图之间的差异，并指出：

* 你回答了另一个问题；
* 这个结论没有证据；
* 这段代码虽然能运行，但改变了原有语义；
* 你遗漏了关键约束；
* 你只是描述完成，并没有真正完成；
* 这条路线已经连续失败，应当停止。

在人类退出局部循环后，需要长程可靠性的 Agent 必须把这种功能系统化。

让 orchestrator 再反思一次有助于发现浅层错误，但它本身不等于建立了审计机制。

---

### 为什么不能只让编排器审计自己

编排器的主要职责是：

* 解释当前任务；
* 选择下一步；
* 调用能力；
* 组织执行；
* 推动任务向前。

它天然带有推进偏好。它已经接受了当前问题表述、计划结构和执行路线。

如果同一个编排器再负责判断：

* 自己的问题定义是否错误；
* 自己选择的路线是否应被推翻；
* 自己生成的结果是否真正满足目标；
* 自己是否已经完成任务；

那么审计很容易退化成对原有叙事的补充说明。这不是说编排器不能做任何自检，而是说自检不应成为高风险提交的唯一依据。

尤其是当编排和审计共享同一份上下文、同一组假设和同一种目标压缩时，审计只是从相同盲区重新采样。

多调用一次模型，并不会自动创造独立性。

---

### 有效审计需要分离的证据路径和否决能力

Agent 中的审计机制应当：

1. 面向任务目标、约束和已提交状态，而不是面向编排器的自我解释；
2. 直接检查产物、观察和证据；
3. 区分 claim、evidence 与 corrective action；
4. 能够指出失败属于哪个机制层；
5. 能够阻止提交、触发修复或要求回退；
6. 不因编排器已经投入大量成本就默认接受当前路线；
7. 具有与风险相称的上下文隔离和权限边界。

审计器也可以由同一种甚至同一个 LLM 驱动。这里的独立性是操作上的，而不一定是模型身份上的；它的价值不来自“换了另一个人格”，而来自：

* 输入结构不同；
* 目标函数不同；
* 接触证据的方式不同；
* 不承担推进任务的压力；
* 具有阻止或回退状态提交的权限。

普通团队可以从很轻的分离开始：执行阶段只生成候选产物和回执，审计阶段在一份较干净的上下文中直接读取需求、差异、测试和最终产物。随着风险提高，再增加不同模型、不同工具、人工审批或真正独立的服务。

---

### 本文区分验证与审计

验证回答的是：

> 是否满足一个已经明确的条件？

例如：

* 测试是否通过；
* 文件是否存在；
* 指标是否超过阈值；
* Schema 是否符合要求；
* 阶段退出条件是否全部满足。

审计回答的是：

> 为什么结果仍然不符合任务价值，失败位于哪里，下一步应当修复什么？

验证更像 gate。
审计更像失败定位和纠正机制。

术语在不同团队中可以不同，关键是保留两种责任：按已知条件判定，以及在结果仍不对时定位缺口。复杂或高风险 Agent 需要二者，不能把它们都压缩成编排器的一次“请检查自己的工作”。

---

## 十二、Agent 的完成必须是状态提交，而不是语言判断

在 Chat 中，模型可以说：

> “以上就是完整方案。”

是否真的完整，由人类判断。

在 Agent 中，如果系统直接把模型的完成声明当成任务结束，就会产生严重的虚假完成问题。

Agent 的完成条件应按任务风险预先定义，通常包括：

```text
所有必要产物存在
+ 所有退出条件满足
+ 必要验证已经运行
+ 高风险问题已经关闭或明确接受
+ 权威状态已成功提交
+ 最终产物与任务目标建立明确对应
```

因此，“完成”不是一个语言标签，而是一种受治理的状态转移：

$$
S_{\text{in progress}}
\xrightarrow{\text{exit criteria + verification}}
S_{\text{completed}}
$$

LLM 可以申请完成；运行时可以按预先授权的规则接受这一申请，但不能把模型的自然语言声明本身当成完成证据。

同样：

* 模型可以申请关闭阶段；
* 模型可以申请接受某项假设；
* 模型可以申请替换权威产物；
* 模型可以申请改变路线；

但这些申请必须经过对应机制提交。

---

## 十三、Agent 架构应当把哪些对象提升为一等治理对象

对于 Chat，中心对象可以是：

```text
Model
Message
Conversation
Tool Call
Memory Item
```

对于 Agent，更合理的一等治理对象应当是：

### Mission

定义长期任务的目标、范围、成功条件和治理策略。

### Task State

定义当前已经成立什么、尚未完成什么、下一步允许发生什么。

### State Transition

定义动作、观察、验证和提交之间的关系。

### Capability

定义一个系统在什么条件下能够承担哪类任务，以及输出如何被验证。

### Artifact

定义产物的身份、版本、依赖、权威性和生命周期。

### Evidence

定义某个 claim 为什么可以被接受、拒绝或继续保持未决。

### Stage

定义长程任务中的稳定边界、退出条件和可回退范围。

### Audit Result

定义失败位置、证据、影响范围和纠正动作。

### Commitment

定义某个候选结果何时从“模型输出”升级为“任务事实”。

LLM 在这个架构中仍然是核心能力提供者，但它更像一个可替换、可组合、可约束的认知执行器。

系统不应围绕“这个模型正在想什么”设计，而应围绕“任务当前处于什么状态、需要什么能力、什么结果可以被提交”设计。

---

## 十四、只以模型为中心会放大哪些结构性风险

当 LLM 被设为唯一中心、其他机制都只是 prompt 的附属品时，系统容易出现以下退化。它们不是每次都会发生，但任务越长、写入越不可逆、验证越困难，风险越高。

### 状态退化为 prompt 中的一段描述

模型需要每次重新解释，而不是读取明确的状态对象。

### 计划退化为模型当前的叙事

计划没有版本、提交、依赖和撤销语义。

### 工具退化为模型可以调用的函数列表

系统只知道工具名称，却不知道它们在不同任务状态中的合法性和风险。

### 审计退化为一次反思提示词

没有独立证据、没有否决权、没有状态提交作用。

### Memory 退化为上下文补丁

所有历史内容被重新注入，却没有权威、有效期和语义类型。

### 多 Agent 退化为多个模型互相说话

如果所有 Agent 都围绕同一段叙事工作，没有共享的权威任务状态，没有明确的提交协议，那么多 Agent 只是扩大了候选意见的数量，并没有建立真正的治理。

### Completion 退化为自然语言结论

模型认为“已经足够好”，系统便停止运行。

这些系统可能在演示中表现流畅，却会在真正长程运行时暴露出漂移、震荡、反复返工、状态污染和无法可靠交付的问题。

---

## 十五、从 Chat 到 Agent，不只是增加组件，更是迁移人类控制面

Chat 向 Agent 的真正转变可以描述为：把人类在 Chat 中隐式承担的职责，逐项迁移到显式系统机制。

| Chat 中的人类职责 | Agent 中需要的外部机制   |
| ----------- | ---------------- |
| 记住目标和进度     | 权威任务状态           |
| 判断哪些信息可信    | Evidence 与验证     |
| 发现回答偏题      | 分离式审计或人工检查      |
| 决定下一步做什么    | 状态感知路由           |
| 决定是否换方法     | 失败分类与路线治理        |
| 区分设想和事实     | 候选—提交分离          |
| 判断任务是否完成    | 退出条件与完成 gate     |
| 纠正错误状态      | 回退、撤销和重放         |
| 控制风险和权限     | 外部权限机制           |
| 保留最终版本      | Artifact 权威与版本治理 |

这张表揭示了一个关键事实：

> Agent harness 不只是围绕模型新增的一层工具，也是人类退出逐步控制循环后，对缺失控制面的系统化承接。

这不意味着人类必须被完全替代。审批点、风险接受和需求裁决仍然可以属于整个 Agent 系统；必须消失的依赖，是“默认有人在每一步替系统记住并纠正一切”。

## 十六、按风险实施的 Agent 设计原则

从以上分析可以导出一组原则。它们的实现强度应随任务时长、开放度、可逆性、验证难度和副作用风险而变化。

### 1. 任务状态优先于对话状态

Agent 首先是一个持续推进的任务系统，其次才是一个语言交互系统。

### 2. LLM 输出默认是候选，不是事实

计划、结论、状态说明和完成声明应经过与风险相称的提交机制。预先授权的低风险副作用可以直接执行，但执行回执仍不等于质量已验证。

### 3. 状态应当在 LLM 之外维护

不是让 LLM“记住状态”，也不是仅记录 workflow 节点，而是由 runtime 或具有同等职责的组件维护语义明确的任务状态。

### 4. 关键上下文从状态渲染

长程任务不应只依赖模型从长对话中重新推断任务事实。

### 5. 状态更新需要适当的观察和验证

模型意图不能替代环境结果，执行描述不能替代真实执行；验证强度取决于错误成本。

### 6. Memory 不能替代机制

用户、环境、任务、Session、证据、产物、权限和决策必须在机制层区分。

### 7. 区分编排、执行、验证和审计

它们可以共享模型和基础能力，但不应共享一套无差别的输入、目标和提交权。风险越高，隔离应越强。

### 8. 异构任务按能力和状态路由

复杂 Agent 不应把所有问题都还原成一次通用模型调用；简单任务可以保留固定路线。

### 9. 执行可以动态，治理边界应当稳定

允许模型灵活搜索，但状态提交、权限、验证和阶段边界不能随模型叙事变化。

### 10. 完成是一种受验证的状态转移

模型的“感觉已经完成”不能代替退出条件。

### 11. 为有代价的动作设计撤销、回退或补偿

长程运行不可能完全避免错误，关键是错误不能无痕污染后续状态。

### 12. 人类升级是合法状态，而不是系统失败

当缺少足够证据、能力或验证边界时，暂停和请求人类介入，优于在不确定叙事中继续推进。

## 十七、普通团队如何落地：一个最小可行治理栈

不必先构建一套宏大的“Agent 操作系统”。对普通应用 Agent，下面七个对象已经能消除大量常见故障：

| 最小对象 | 至少记录什么 | 最简单的实现 |
| --- | --- | --- |
| Task Spec | 目标、范围、约束、验收条件 | 版本化 JSON/YAML 或数据库记录 |
| State Record | 当前阶段、已接受事实、未决项、阻塞 | 带版本号的结构化状态 |
| Action Proposal | 动作、理由、预期副作用、所需权限 | 类型化工具调用 |
| Execution Receipt | 实际调用、返回、时间、目标版本 | 不可变日志或事件记录 |
| Evidence | 哪条证据支持哪个结论 | 测试报告、查询结果、产物哈希 |
| Gate | 何时可提交、何时拒绝或升级 | 规则代码加必要的语义审查 |
| Commitment | 新权威状态、提交者、依据、可回退点 | 事务、版本提交或状态事件 |

一次最小状态转移可以写成：

```text
读取版本化任务状态
→ LLM 提出类型化动作
→ runtime 检查权限与前置条件
→ 工具执行并返回回执
→ verifier 检查退出条件
→ commit 新状态，或记录失败并选择修复/升级
```

### 一个代码修复例子

用户要求修复一个 API Bug。模型生成补丁只是 `Action Proposal`；文件写入和命令输出是 `Execution Receipt`；针对复现用例的测试、回归测试和 diff 检查构成 `Evidence`；只有 Gate 接受这些证据后，状态才从“修复中”变为“已完成”。如果测试环境缺失，合法的非完成状态可以是“阻塞：需要环境信息”，而不是编造一个完成声明。

### 什么时候不需要重治理

如果任务短、结果可立即人工检查、动作完全可逆、没有外部副作用，而且失败成本很低，那么聊天记录、一个工具循环和最终人工验收可能已经足够。不要为了架构纯度引入复杂状态机。本文的主张不是“所有 Agent 都要重型治理”，而是：

> **一旦系统开始替人维护长程任务真相，它就必须以与风险相称的方式承接这份权威。**

## 十八、Chat、Bot 与 Agent 的最终区别

可以把三者的核心结构压缩为三句话。

### Chat

> 人类维护任务，LLM 参与思考。

### Bot

> 人类委托一个局部功能，并保持监督和最终验收。

### Agent

> 人类委托一个持续任务，系统必须承接人类不再逐步承担的治理职责，并在必要时把问题升级给人。

因此，三者真正的差异不是模型能力，而是任务权威位于哪里。

| 维度                 | Chat  | Bot     | Agent                             |
| ------------------ | ----- | ------- | --------------------------------- |
| 人类是否逐步在环           | 是     | 通常是     | 通常否；可在检查点重新进入                     |
| 任务状态权威             | 人类    | 人类或固定系统 | 外部任务治理层                           |
| LLM 输出性质           | 建议    | 局部结果    | 候选动作与候选结论                         |
| 偏移纠正               | 人类    | 人类或固定规则 | Agent 自身治理机制                      |
| 路由                 | 人类决定  | 预设或人类决定 | 固定路线或状态感知的能力路由                    |
| 审计                 | 人类    | 人类或简单检查 | 与风险相称的分离式审计                      |
| 完成权                | 人类    | 人类或固定流程 | 退出条件与验证提交                         |
| Memory 的主要作用       | 连续性   | 便利与局部记录 | 只能作为底层存储之一                        |
| 中心治理对象             | 模型与对话 | 功能与模型   | Mission、State、Capability、Evidence |
| Harness 的意义        | 调用便利  | 功能封装    | 用外部治理约束模型不确定性                     |

## 结语：Agent 是一种新的软件制度

Chat 和 Bot 的成功，部分建立在一个被长期忽略的事实之上：人类始终在承担最困难的治理工作。

人类维护真实意图，补齐隐含状态，发现模型偏移，决定下一步路线，区分假设与事实，并最终判断任务是否完成。模型只需要在局部提供高质量认知输出。

Agent 改变了这个前提。

当人类退出逐步控制循环后，系统不能假设这些治理职能仍然存在，也不能简单地把它们交给一个依赖上下文、概率生成并可能发生漂移的 LLM。

因此，Agent 不是一个更自主的 Chat，也不是一个增加了 memory、tools 和 loop 的 Bot。

Agent 是一种不同的软件制度：

> **它以任务状态而不是对话历史为中心，以能力而不是模型调用为基本单元，以验证后的状态提交而不是自然语言声明作为进展，以分离式审计而不只是自我反思作为纠偏，以外部规则治理模型的不确定性。**

在 Chat 中，系统可以以 LLM 和对话为中心，因为人类是隐藏的任务操作系统。

在 Agent 中，LLM 仍可以是一等能力对象，却不能成为唯一的最高任务权威；Agent harness 必须承接人类不再逐步提供的控制面。

真正需要被提升为一等对象的，不是“模型正在说什么”，而是：

> **任务当前处于什么状态，哪些结果已经成立，下一步允许发生什么，以及什么证据足以让系统继续前进。**

只有完成这一转换，系统才从“无人看管的对话模型”真正变成能够长程、稳定、可审计地承担任务的 Agent。
