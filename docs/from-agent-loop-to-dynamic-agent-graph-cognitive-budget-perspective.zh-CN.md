# 从 Agent Loop 到动态 Agent Graph：认知预算的视角

## Route、Workflow 与 Graph 的统一解释

### 摘要

为什么一个最初只需“观察—思考—行动”的 Agent Loop，最终会演化出路由器、专用 Workflow、并行分支、审计节点、恢复流程、Human Gate，以及运行时动态生成的 Agent Graph？

常见解释通常停留在两个层面：复杂任务天然具有图结构；或者 LLM 的隐式判断一旦被外置，控制流就会展开成图。这两种解释都成立，却仍主要描述了 Graph 的**形状**，没有说明系统为什么必须付出额外的编排成本去获得这种形状。

更深层的驱动力是：**不同问题方向需要不对称、持续、受保护且带验收条件的认知投入，而自由运行的单一 Loop 无法稳定承诺这种投入。**总 token 更多，并不意味着关键方向会得到足够预算；模型仍可能提前满足、沿首个假设自洽、频繁切换方向，或在生成后自行验收。真正需要被工程化的，不只是预算总量，而是预算的方向、期限、操作策略、状态、停止条件与验收权。

在这一视角下：**Route 是一次认知投资决策；Workflow 是这项投资的执行合同；Graph 是多次投资承诺之间的依赖结构与运行账本。**Graph 并不取代 Loop。Loop 仍是局部推理和行动的基本执行器，Graph 则负责决定有限智能预算应投向哪里、持续多久、以何种方式运行，以及凭什么结束。

**关键词：** Agent Loop；动态 Agent Graph；认知预算；Workflow；Route；Residual；Oracle；认知资本配置

## 一、真正的问题不是“为什么任务像图”，而是“为什么系统需要承诺”

基础 Agent Loop 极其自然：模型观察当前上下文，选择下一步行动，读取行动结果，再继续推理。对于短任务、反馈及时的任务，或者可以由一次局部判断完成的任务，这种结构已经足够。

当任务变长、目标变多、反馈变弱时，Loop 往往逐步长出规划、路由、审计、恢复、并行搜索、聚合与人工审批等结构。对此，最常见的解释有两种。

第一种解释是：**复杂任务本来就具有依赖、分支、汇合与回退，因此天然适合图结构。**这说明了任务结构为什么能被图表达，却没有解释为什么控制系统不能继续由一个通用 Loop 临场处理这些依赖。

第二种解释是：**原本隐藏在 LLM 内部的“下一步做什么”被外置为显式控制节点，于是 Loop 展开成了 Graph。**这说明了图如何出现，却仍未回答：为什么这些判断值得被外置？为什么不能继续让模型自行判断？

更根本的答案是：复杂任务中存在许多具有延迟收益的认知方向。它们在最初几步往往不会立即改善最终产物，甚至会暂时降低表面进度。例如，沿一个反例追查到底、重新获取一手证据、独立重建候选、验证依赖链、对多个方案进行公平比较，都会推迟“看起来已经完成”的时刻。

自由 Loop 擅长局部推理，却不擅长对这些方向作出**持续承诺**。它可以在当前 turn 决定“现在审计一下”，却无法保证下一 turn 不被一个看似合理的修补方案吸引；可以生成多个候选，却无法保证不会在看到第一个可用候选后提前收敛；可以声明要查询证据，却可能在搜索成本刚刚出现时退回内部猜测。

因此，Agent 从 Loop 演化为 Graph 的真正驱动力，不是“任务需要画成图”，而是：

> **系统需要把原本由模型逐 turn 临场支配的认知预算，改造成可以被承诺、隔离、追踪、验收和重新配置的工程对象。**

## 二、认知预算不只是 token，而是“资源加支配规则”

在 Agent 系统中，“预算”经常被简化为 token 数、模型调用次数或运行时间。这种定义过窄。真正影响结果的，是一组共同决定认知投入方式的资源：

- 模型推理 token 与调用次数；
- 可占用的上下文窗口与上下文质量；
- 工具调用、外部检索和环境交互次数；
- 候选数量、搜索宽度与验证轮数；
- 可保存的中间状态、证据和版本；
- 延迟、计算费用与人类注意力；
- 对副作用、权限和真实环境操作的容许范围。

更重要的是，同样的资源总量可以产生完全不同的结果。决定差异的，不只是“有多少”，而是以下问题：

1. 预算被投入哪个问题方向；
2. 该方向至少能连续运行多久；
3. 其他目标能否中途抢占它；
4. 运行时允许使用哪些上下文、工具与动作；
5. 中间发现是否被持久保存并参与后续判断；
6. 继续投入需要满足什么进展条件；
7. 谁拥有成功判定权；
8. 何时停止、升级、回退或转交人类。

因此，认知预算更准确的定义是：

> **认知预算 = 稀缺推理资源 + 对这些资源的方向、期限、策略、状态与验收权的治理。**

从这个定义出发，“多给 Loop 一些 token”只增加了资源总量，却没有改变预算支配机制。新增 token 仍然是可自由挪用的：模型可以把它们花在重复解释、继续自洽、生成更多相似候选、修饰已有答案，或者过早地论证自己已经成功。系统获得了更多计算，却没有获得对关键认知方向的投资保证。

## 三、自由 Agent Loop 的结构性短视

一个未经约束的 Agent Loop，通常在每一步重新选择当前看来最合理的行动：

```text
观察当前状态
→ 选择眼下收益最高的 action
→ 获得局部结果
→ 更新判断
→ 再次选择 action，或宣布完成
```

这种机制并不等于模型“能力不足”。问题在于，它把所有长期方向都降格为逐 turn 续租的临时意图。任何方向只有在每一个中间时刻都继续显得最值得做，才能获得下一步预算。

这会产生四类典型短视。

### 1. 提前满足：局部可接受替代全局完成

一旦出现一个流畅、合理、看似覆盖主要要求的答案，Loop 就容易把“已经存在可用解”误当成“剩余 residual 已经足够小”。而反例搜索、边界检查、证据补全和全局一致性验证的收益通常滞后，因而最容易被取消。

### 2. 路径依赖：第一个假设获得持续复利

Loop 的上下文由先前输出构成。首个假设一旦被写入，就会不断获得后续 token 的解释、补充与修复。即使系统名义上仍可改变方向，切换成本也越来越高。更多预算可能因此强化最早的路径，而不是扩大真实搜索。

### 3. 方向切换：认知投入不断被重新分配

研究、生成、审计、修复和总结需要不同的行为策略。自由 Loop 在这些方向之间频繁切换时，中间假设、证据链和局部目标容易被压缩成模糊摘要。预算看似一直在消耗，单一方向却没有形成足够深度。

### 4. 职责污染：生成者同时拥有验收权

当同一上下文、同一轨迹和同一目标驱动生成与验收时，验证很容易退化为对已有答案的解释。模型不是完全不能发现错误，而是生成轨迹已经改变了它接下来最容易看到什么、愿意保留什么，以及何时认为任务可以结束。

这些问题共同指向一个核心缺口：

> **自由 Loop 拥有局部行动能力，却缺少跨多步保护某个认知方向的承诺机制。**

如果给 Loop 加入不可抢占的方向、持久状态、专用动作空间、外部 oracle 和明确停止条件，它当然也可以完成长期投入。但此时，它已经不再是纯粹的自由 Loop，而是在结构上成为了一个 Workflow。真正的分界不在名称，而在预算控制权是否仍完全属于模型的逐步临场判断。

## 四、从 Action 到 Workflow：预算承诺的最小结构

为了避免概念膨胀，需要区分 Action、Tool 与 Workflow。

- **Action** 是一次原子操作，例如读取文件、运行测试、查询网页、生成一个候选。
- **Tool** 提供某类可调用能力，例如搜索、代码执行、数据库访问或浏览器操作。
- **Workflow** 是围绕一个明确问题方向运行的、带状态与验收条件的多步策略。

调用一次搜索工具不是 Research Workflow；换一个“审计提示词”也不自动构成 Audit Workflow。Workflow 之所以值得成为独立控制单元，是因为它对一段未来行为作出了可执行承诺。

可以把一个 Workflow 抽象为如下合同：

```text
Workflow = {
  target:        要处理的问题方向或 residual，
  input:         可接受的输入与前置依赖，
  public_contract: 对外承诺的输入、输出、证据、决策与 residual schema，
  context:       可见、不可见和必须重新获取的上下文，
  private_state: 不向下游暴露的 scratchpad、搜索轨迹与实现细节，
  action_space:  允许使用的工具、动作与副作用边界，
  state:         必须持久保存的假设、证据、候选与进度，
  budget:        最低预算、最大预算及资源类型，
  progress:      继续投入所需的新证据或 residual 降幅，
  oracle:        判断局部成功、失败或不确定的机制，
  exit:          停止、升级、回退和转交条件，
  output:        返回给外层控制器的结构化结果
}
```

这一定义揭示了 Route 与 Workflow 的本质区别：

> **Route 是一次认知投资决策；Workflow 是这项投资的执行合同。**

Route 回答“下一份智能预算投向哪里”；Workflow 回答“这份预算以何种方式被持续投入，并由什么条件结束”。

以 `route → audit workflow` 为例，它不只是把系统提示改成“请审计”。它应当在合同层面完成以下变化：暂时冻结继续扩写或修饰原方案；把预算专门投入反例、冲突、边界和证据检查；使用不同于 builder 的上下文组织方式；限制直接重写产物的冲动；持久记录 finding、evidence、severity 与 unresolved claim；并由审计完成标准决定何时返回，而不是由“已经看起来不错”决定何时结束。

不同 Workflow 固化的是不同的认知轴：

| Workflow | 被保护的认知方向 | 典型局部产物 |
|---|---|---|
| Research | 外部证据获取与来源核验 | evidence、provenance、uncertainty |
| Candidate Search / Governed Iteration | 候选探索、边界推进与受控迭代 | candidate、state transition、gate result |
| Audit | 反例搜索、冲突发现与缺陷定位 | finding、evidence、severity、corrective target |
| Recovery | 围绕特定 residual 的闭环修复 | patch、retest result、remaining residual |
| Fan-out | 假设、方案或子问题的受控分化 | independent branches、candidate set |
| Fan-in | 冲突消解、聚合与全局一致性 | merged result、conflict ledger、global residual |
| Human Gate | 规格、价值判断、授权与风险边界澄清 | decision、constraint、approval / rejection |

SGAR 不应在这张表里被当作与 Research、Audit 或 Recovery 并列的 Workflow。SGAR 是治理这些 Workflow 如何读取权威状态、如何提交公共增量以及如何被验收的运行体制；候选搜索只是其中一种可能的局部求解方向。

Workflow 不是角色名称，而是一条被制度化的认知投资方向。若它没有独立状态、不同策略、明确 oracle 和退出合同，就很可能只是一个 prompt 模板，而不是值得进入 Graph 的控制节点。

## 五、预算包络：既防止过早放弃，也防止无限消耗

“为某个方向固化预算”仍然容易让人误解为预先分配一个刚性的 token 数。更准确的概念是**预算包络**：它为某个认知方向规定投入的下限、上限、继续条件和停止条件。

### 最低预算：防止方向刚启动就被取消

许多高价值方向需要经过若干无明显产出的步骤，才可能出现有效证据。最低预算保证 Workflow 在尚未显现收益时，不会仅凭局部观感被提前终止。最低预算可以是最少验证轮数、最少独立候选数、必须检查的关键声明数，或必须覆盖的证据类型，而不一定只是 token。

### 最大预算：防止错误方向形成黑洞

认知承诺不能变成无限承诺。错误假设、低带宽 oracle 或不可解 residual 都可能吞噬大量资源。最大预算要求 Workflow 在达到资源上限后返回当前证据、失败类型和未解决项，由外层重新路由，而不是在内部无限自循环。

### 进展条件：预算只能被“新信息”续期

Workflow 是否继续，不应只取决于“还有预算”，而应取决于是否获得了新证据、排除了候选、降低了 residual、缩小了不确定性，或改善了可测指标。重复同一解释、生成高度相似的候选、再次报告同一错误，不应被计算为有效进展。

### 停止条件：耗尽预算不等于成功

成功必须由 oracle、明确 No-Go、不可解证明、风险阈值或 Human Gate 触发。预算耗尽只意味着该次投资合同结束，并不自动意味着任务完成。

因此，合理的 Workflow 不是“给一个子代理固定 20,000 token”，而是：

> **为一个认知方向建立带下限、上限、持续状态、进展门槛和验收条件的预算包络。**

## 六、为什么“给 Loop 更多预算”不等价于 Workflow

在资源总量相同的前提下，自由 Loop 与 Workflow 的差异不是模型能力，而是预算治理结构。

### 1. Workflow 保护注意力方向

一旦进入某个 Workflow，系统在一段时间内不再重新竞价所有可能目标。审计预算不能被拿去继续生成，研究预算不能被拿去润色结论，恢复预算不能被另一个新想法轻易抢占。方向保护让具有延迟收益的工作获得完成机会。

### 2. Workflow 改变操作策略，而非只改变角色措辞

不同方向应当具有不同的上下文、工具优先级、动作许可和副作用边界。Research 需要优先外部取证；Audit 需要主动构造反例并避免直接代写；Recovery 需要最小修改和原 oracle 重跑；Fan-in 需要处理冲突与全局约束。仅靠一个通用 Loop 临场切换，很难稳定维持这些策略差异。

### 3. Workflow 建立可持续的局部状态

证据表、候选集、失败分区、已排除假设、版本差异和验证结果，需要以结构化状态存在，而不是只作为长对话中的自然语言残留。持久状态使认知投入可以累积，而不是每轮重新压缩、重新解释。

### 4. Workflow 将成功判定绑定到外部条件

自由 Loop 常以语义流畅、主观完整或“已经做了很多工作”作为隐式停止信号。Workflow 把停止权交给 oracle、gate、residual 阈值或明确的升级规则，从而把“模型感觉完成”与“系统接受完成”分离。

### 5. Workflow 可以实施职责分离

生成、验证、授权和全局验收不必由同一轨迹完成。职责分离并不保证验证者永远更聪明，却能减少生成路径对验收标准的污染，并允许验证方向使用不同证据和动作约束。

所以，两者的差别可以概括为：

> **增加 Loop 预算，是增加可自由支配的计算；建立 Workflow，是改变一部分计算的支配权。**

若一个所谓的“更强 Loop”已经具备方向锁定、状态持久化、专用 action space、外部 oracle 与受控退出，那么它与 Workflow 的差别只剩命名。这里批评的不是循环结构本身，而是没有预算承诺能力的自由循环。

## 七、Graph 如何从 Residual 驱动的预算配置中产生

当系统只有一个自由 Loop，外层控制器的决策粒度是单步 Action：

```text
选择下一步 action
```

当系统拥有 Workflow 后，决策粒度变为一段受约束的多步 policy：

```text
选择一个问题方向
→ 实例化相应 Workflow
→ 在预算包络内执行
→ 返回结构化 outcome / residual
```

而一次 Workflow 的结果通常不会简单地把任务变成“完成”或“未完成”。它可能产生：

- 新 residual 与新的失败层级；
- 新证据、反证或不确定性；
- 新候选与候选间冲突；
- 需要补齐的前置依赖；
- 可并行处理的子问题；
- 必须交由 Human Gate 的规格或授权问题；
- 对先前节点的回退、重跑或版本分叉要求。

这些 outcome 决定下一份认知预算应该投向哪里。于是运行时控制流自然变为：

```text
workflow
→ outcome / residual
→ route
→ next workflow
→ fan-out / fan-in / retry / rollback / human gate
→ global acceptance
```

这就是动态 Agent Graph 的来源：

> **Graph 是多次认知预算承诺之间形成的依赖结构。**

可以把任一时刻的系统表示为一个不断增长和重写的运行图：节点不是抽象“角色”，而是具体的 Workflow 实例；边也不只是先后顺序，而可以表示依赖、证据支持、反证冲突、residual 转移、重试、回退、聚合和授权关系。

因此，动态 Agent Graph 不必是 DAG。真实系统可能包含恢复循环、审计回流、版本回退与重新规划。静态 DAG 是预先承诺好的预算日程；动态 Graph 则根据运行结果和 residual 条件化地实例化下一段预算合同。

从这个角度看，图的拓扑不是首要设计目标，而是运行决策的结果。真正的外层控制问题是：

```text
在当前状态、残差、风险与剩余预算下，
哪一种 Workflow 能带来最大的预期全局 residual 降幅？
```

可以用一个简化的路由目标表达：

```text
选择 W*
= 最大化 [预期任务价值增量或 residual 降幅
          - 资源成本
          - 副作用风险
          - 编排与协调开销]
```

Graph 则保存这些选择的依据、依赖和后果，使系统能够回答：预算为何投入该方向、产生了什么证据、哪些 residual 被关闭、哪些仍未关闭，以及下一次路由应继承哪些状态。

残差路由在这里是反馈机制，而不是 SGAR 或 Graph 的第一原理。它读取已提交状态，选择下一份认知预算投向，并塑造下一 Workflow 的公共协议；它不能独自决定什么已经成为系统事实。即使路由来自固定规则、人类或其他控制器，只要局部求解仍受全局权威状态约束、结果仍经验证提交，状态治理关系依然成立。

整个演化可以浓缩为三句话：

> **Route 选择把智能投入到哪里。**  
> **Workflow 保证该方向得到怎样的持续投入。**  
> **Graph 记录并组织这些投入之间的依赖关系。**

---

## 八、Graph 的全局职责：避免“局部通过、整体失败”

把多个 Workflow 连接起来，并不自动得到全局最优结果。每个 Workflow 都可能只优化自己的局部 oracle：Research 找到了可靠证据，Audit 找到了真实缺陷，Recovery 修复了局部错误，多个候选也分别通过了各自检查，但最终产物仍可能相互冲突、遗漏全局约束或破坏其他已通过部分。

因此，Graph 的价值不仅是分发预算，还包括维护**局部成功与全局成功之间的边界**。

这里的“全局”不是把全部代码、历史和所有分支私有状态复制给每个 Workflow。外层状态保存总体目标、非目标、系统不变量、跨阶段依赖、已冻结决策、当前证据、未解决变量、authority 和生命周期约束；每个 Workflow 只接收足以支持当前判断的最小充分投影。

局部之间也不应通过完整私有轨迹耦合。跨 Workflow 的公共 handoff 应收敛为：

```text
contract delta
accepted evidence
committed decision
remaining residual
```

如果某项私有假设或实现事实会影响下游正确性，它必须被提升为公共证据或协议条款。否则下游既无法验证它，也无法在替换上游实现后继续工作。

在阶段化实现中，这形成“阶段提交串行化、阶段求解可并行化”的结构：有真实依赖的阶段通过验收屏障推进；同一阶段内部，在相同状态快照和公共协议下相互独立的问题可以组成小型 DAG 并行求解。Fan-in 负责把候选收敛成可提交的公共增量，而不是拼接私有推理。

Fan-in 不应被理解为简单摘要。真正的 Fan-in 需要：

- 对齐不同分支的输入假设与版本；
- 保留证据来源和不确定性，而不是只保留结论；
- 显式记录候选冲突和无法合并的约束；
- 检查局部修改是否造成跨模块副作用；
- 重新计算全局 residual；
- 由全局 acceptance oracle 决定是否关闭任务。

这意味着 Graph 同时维护两类账本：一类是**认知投资账本**，记录预算投向与产出；另一类是**任务状态账本**，记录依赖、版本、residual 与验收状态。没有前者，系统不知道资源为何被消耗；没有后者，系统无法判断局部成果是否真正改变了全局任务状态。

## 九、判断一个 Workflow 是否值得存在

认知预算视角不仅解释 Graph 为什么出现，也提供了一把裁剪 Graph 的工具。Workflow 越多，不代表系统越强。每增加一条分支，都会增加路由错误、状态同步、上下文转换、结果聚合和可观测性成本。

一个认知方向通常只有在满足以下条件时，才值得被提升为独立 Workflow：

### 1. 收益具有延迟性

该方向需要连续多步投入，早期步骤不一定立即改善最终产物，因而容易被自由 Loop 提前放弃。

### 2. 需要不同的操作策略

它确实需要不同的上下文、工具优先级、action space、权限或副作用边界，而不只是换一个角色名称。

### 3. 中间状态具有累积价值

假设、证据、候选、版本、排除项和进展记录需要持续保存；若每一步都可独立完成，则更适合作为 Action 或 Tool。

### 4. 存在可定义的局部 oracle

系统至少能够判断该 Workflow 是否取得进展、是否通过、是否 No-Go，或是否应升级。完全无法验收的分支容易变成预算黑洞。

### 5. 该方向存在高抢占或高污染风险

例如生成会挤占审计、已有假设会污染独立重建、局部修复会遮蔽根因、一个分支会垄断全部搜索预算。

### 6. 结构收益超过编排成本

同等资源下，它应当提升全局成功率、residual 降幅、证据质量或稳定性；否则就应被合并、降级为普通 Action，或仅在特定 residual 下条件触发。

一个非常实用的反向判据是：

> **如果删除该 Workflow，只给通用 Loop 相同资源、相同工具和相同 oracle，结果没有显著变差，那么该 Workflow 很可能没有独立存在的结构价值。**

尤其需要警惕“角色型 Workflow”：它只改变 system prompt 中的身份，却没有改变预算包络、状态结构、行为许可和验收条件。这类节点会制造 Graph 的表面复杂度，却没有形成真正的认知投资合同。

## 十、如何用等预算实验验证结构价值

验证 Workflow 的正确对照，不是“小预算 Loop”与“大预算 Workflow”，而是严格的**等预算对照**。

### 基础实验

- **A 组：** 自由 Agent Loop；
- **B 组：** 路由后进入专用 Workflow；
- **C 组：** 由 residual 动态选择多个 Workflow 的 Agent Graph。

三组应尽量保持相同模型、总 token、调用次数、工具能力、初始信息、总体时间和 oracle 可访问性。若 B 组拥有审计工具，A 组也应能调用同一工具；区别在于 A 组可自由分配预算，而 B 组必须按审计合同持续执行。这样才能把“能力差异”与“预算治理差异”分开。

### 核心指标

最终指标必须以全局验收为中心，而不能只看某个节点的局部得分：

- 全局 acceptance 成功率；
- 单位预算的 residual 降幅；
- residual 随预算变化的曲线，而不只是终点；
- 提前结束率与未关闭 residual 数量；
- 新证据获取量、证据有效率与来源独立性；
- 候选覆盖度及候选比较公平性；
- 重复工作、无效候选和方向切换次数；
- 副作用、回退次数与局部修复造成的回归；
- 错误路由率、路由后悔值与编排开销；
- 不同运行之间的结果方差与稳定性。

### 机制消融

若 B 组优于 A 组，还需要进一步拆分收益来自哪里。可以逐项消融：

- 只保护方向，不隔离上下文；
- 只持久化状态，不改变 action space；
- 只绑定 oracle，不设置最低预算；
- 只做职责分离，不动态路由；
- 只设置最大预算与 no-progress gate；
- 固定 Graph 与 residual 驱动的动态 Graph 对比。

这类实验能够回答：真正产生收益的是方向保护、状态累积、策略切换、独立验收，还是仅仅增加了调用次数。

结论的解释应当非常严格：

- 若 B 只因消耗更多资源而胜出，收益来自预算总量，而非 Workflow 结构；
- 若等预算下 B 显著更好，说明预算承诺产生了结构价值；
- 若 B 只在某类 residual 上有效，应把它改成条件路由，而非默认流程；
- 若协调成本抵消收益，应删除、合并或缩短该 Workflow；
- 若 C 不优于 B，动态 Graph 可能只是增加了路由复杂度，并未改善资本配置。

## 十一、动态 Agent Graph 的主要风险

把认知预算外部化并不自动保证正确。Graph 只是把新的控制能力交给工程系统，同时也引入新的失败模式。

### Graph 官僚化

过多节点、格式和交接会把预算消耗在包装状态、重复总结和上下文搬运上。解决办法不是继续增加协调节点，而是要求每个 Workflow 证明等预算下的边际价值。

### 错误路由

若 residual 分类错误，系统可能把大量预算投入不相关方向。路由器应返回置信度、备选路径与可逆决策，并允许在 no-progress 时重新分区。

### 局部 oracle 失配

Workflow 可能优化一个容易通过却与全局价值不一致的指标。所有局部通过都必须最终回到全局 acceptance，而不能以节点完成替代任务完成。

### 预算饥饿与分支垄断

高噪声分支可能持续产生“看似新颖”的发现，吞噬其他关键方向的预算。需要全局配额、边际收益监控和最大预算约束。

### 状态分叉与聚合失真

并行分支可能基于不同版本和隐含假设工作。Fan-in 必须保留 provenance、版本和冲突，不能把不可兼容结果强行总结为一个流畅结论。

### 恢复循环与震荡

Audit、Recovery、Replan 之间可能反复往返，却没有真实 residual 下降。no-progress gate、重试上限、失败分区重估和 Human Gate 是必要的终止机制。

因此，Graph 的成熟度不应以节点数量衡量，而应以其能否更有效地分配预算、关闭 residual、控制副作用并维持全局一致性衡量。

---

## 十二、从 Loop 到 Graph 的完整演化链

从认知预算的角度，Agent 架构的演化可以被理解为五个连续阶段：

```text
自由 Loop
→ 带硬停止条件和状态的受控 Loop
→ 可复用的专用 Workflow
→ 基于 residual 的动态 Route
→ 带 fan-out、fan-in、回退与全局验收的动态 Agent Graph
```

这不是从“简单推理”升级到“复杂图框架”的形式演化，而是预算治理权逐步外部化的过程：

1. **自由 Loop** 由模型逐步决定下一份预算投向；
2. **受控 Loop** 开始由外部状态和 gate 限制停止与转移；
3. **Workflow** 对一个认知方向作出跨多步承诺；
4. **Route** 在多个方向之间进行条件化资本配置；
5. **Graph** 维护这些承诺的依赖、并发、冲突、回退与全局验收。

需要特别强调：Graph 并不消灭 Loop。每个 Workflow 内部仍然可以包含 Loop，用于局部观察、推理和行动。真正发生变化的是层级分工：

> **Loop 负责自由的局部推理；Workflow 负责受保护的阶段性投入；Graph 负责全局的预算配置与依赖治理。**

如果把所有事情都交给 Graph，系统会失去局部灵活性；如果把所有事情都交给 Loop，系统又会失去长期承诺。可靠 Agent 需要的不是二选一，而是让自由推理运行在受治理的预算结构之内。

---

## 十三、结语：动态的认知资本配置系统

Agent Loop 为什么会长成动态 Agent Graph？

因为单一自由 Loop 擅长根据局部状态做下一步判断，却不擅长对一个具有延迟收益的方向作出持续、排他、可追踪且带验收条件的承诺。复杂任务真正稀缺的，不只是更多推理，而是让正确的推理方向获得足够长、足够独立、能够累积状态并由正确 oracle 结束的投入。

工程系统为了弥补这一缺口，依次形成了三个层次：

> **Route 决定下一份智能预算投向哪里。**  
> **Workflow 把这项投入变成带边界、状态和验收条件的合同。**  
> **Graph 记录并组织多项投入之间的依赖、冲突、回退与聚合。**

因此，比“Agent Graph 框架”更接近本质的定位是：

> **动态 Agent Graph 是一个认知资本配置系统。它把有限的模型推理、工具调用、上下文、验证机会和人类注意力，持续投入到当前最值得关闭的 residual 上。**

“认知资本”在这里不是对智能进行精确货币化，而是一种工程抽象：认知资源是稀缺的，投入方向存在机会成本，投资可能失败，局部收益不等于全局收益，所有追加预算都应由进展证据证明其合理性。

图的形状只是这些投资决策留下的运行痕迹。真正被工程化的，是三个此前主要由模型临场决定的问题：

> **注意力该往哪里去？应当持续多久？凭什么停止？**

当这三个问题获得了外部状态、预算包络、oracle 和 residual 路由的共同约束，Agent 才从一个会不断采取下一步行动的 Loop，转变为一个能够治理长期认知投入的动态系统。

若把这一结构放回 SGAR，关系应当保持清楚：SGAR 的核心是从全局权威状态生成有全局条件的局部求解面，并只把经过验证的公共增量提交回状态；动态 Graph、阶段验收和残差路由负责实现反馈、依赖收敛与预算配置。前者定义什么样的局部求解可以组合为长期进展，后者决定下一次实际求解什么。
