## 为什么这件事重要

在为一个失败的任务继续投入之前，这一页先帮你回答一个很实际的问题：它是那种"多做一点同样的事"迟早能解决的问题，还是那种再怎么等也解决不了的问题？

如果一个问题最终能靠更大的模型、更长的训练、更好的数据自然解决，那么最合理的策略往往就是等待，或者继续在 prompt 上做边际优化。

但如果一个失败已经触到结构性天花板，继续等待就会变成一种昂贵的误判。你以为自己只是在等模型再强一点，实际却是在错误的任务形态里反复打磨、反复采样、反复润色，把时间消耗在一个不会自动打开的门上。

这就是为什么"为什么重要"必须放在前面。它首先要帮你完成一个判断：眼前的问题究竟还是"继续优化模型使用方式"的问题，还是已经变成"必须重构任务、引入外部控制对象与治理机制"的问题。

## 日常使用中它是什么样子

你让 LLM 做一个困难任务。它先给出一个看起来说得通的答案。你指出问题，它会继续补充细节、改善语气、增加结构、扩展论证。几轮以后，文本变得更漂亮，但你仍然觉得"不对劲"。

这种"不对劲"常常不是文风问题，而是任务价值没有被真正抓住。缺的可能是一个隐藏前提、一项现实状态、一道领域边界、一些少见选项、一处全局依赖、一个授权条件，或者一种更准确的方式去给问题本身建模。模型并不是没有努力，它只是在错误的表面上继续做局部改进。

这也是流畅失败难以察觉的原因。答案可能在很多局部层面有用：压缩了上下文、选了合适语气、补了过渡、组织了结构。但真正的失败只会在这些局部改进没有触及任务价值的决定变量时显现。

这一页做的第一件事，就是把这种"不对劲"拆成可诊断的形态。下一页"案例"是案例库入口：从 Story Insight V4/V6 的控制空间与分层治理，到 Stock Rec V3 的金融生产权治理，再到 FW-Insight V3 的硬经验提取；再往后的"机制"会把案例收束到更稳定的理论轴上：概率与价值是否同向，以及六类原始失配分别指向什么干预。

## 为什么多轮修改也会失败

多轮修改只有在"局部改进方向"和"真实价值方向"一致时才会稳定有用。比如压缩一段文字、改写语气、整理清单，局部变好通常就是真的变好。

**但在高失配任务里，瓶颈不在局部润色，而在任务结构本身：**

:::cards
### 错抽象

模型回答了一个看似相关、但其实不是你真正要解决的问题。它可能把战略判断写成漂亮文章，把诊断任务写成常识建议，把架构问题写成代码片段。

### 缺状态

正确答案取决于当前市场、用户情绪、法律边界、生产环境、时间窗口或组织权限。状态不在上下文里，模型就只能按默认情境生成。

### 缺通道变量

决定性变量存在于真实世界，却没有被当前通道保留下来。照片可能看不出重量或温度；文字转录可能保不住语气；摘要可能漏掉真正决定诊断的日志行。

### 缺尾部方案

真正高价值的答案可能是低概率的，不是模型默认最容易想到的路径。此时多数投票和反复采样可能只会把常规答案越推越稳。

### 缺真实标准

提示里的目标只是代理目标。答案满足了"清楚""完整""专业"，却没有满足真正的成功标准：能否执行、能否验证、是否承担风险、是否符合场景。

### 局部绑定

模型锁定了一个看似合理的解释、指标、话术或早期解法路径。答案在当前场景里很自洽，但换到相邻情形就暴露出绑定过强。
:::

这些日常形态，对应机制层里的六类原始失配：

::::cards
### 错抽象 -> 聚合 / 规格失配

模型不断改善答案的局部组成，却没有抓住全局结构或真实目标。更漂亮的战略备忘录，仍可能只是优化了"论述完整"，而不是"决策清晰"。

### 缺状态 -> 状态失配

模型像是在一个稳定且已知的世界里回答。但退款策略、部署方案或市场建议，都会因为当前状态不同而反转。

### 缺通道变量 -> 观测-表征失配

模型围绕可见代理推理，因为任务充分变量从未进入它的表征。系统需要测量、原始数据、日志、测试、工具反馈或更丰富模态，推理才有资格闭合。

### 缺尾部方案 -> 支持失配

最好的答案未必是统计上最自然的答案。系统需要检索、扰动、反例或显式尾部搜索，把稀缺结构拉到上下文里。

### 缺真实标准 -> 规格失配

模型满足了写出来的代理目标，却没有满足真正的成功条件。"看起来专业"不等于已经验证、授权、可逆或正确。

### 局部绑定 -> 拟合边界失配

模型把局部支持误当成不变量。扰动场景、指标、审计路径或反馈来源，可以检验这个断言是否真的能泛化。
::::

如果你想看更结构化的推导，可以读 [六类原始失配总览](docs/six-primitive-mismatches-pipeline-derived-taxonomy-llm-systems.zh-CN.md) 或其结构基础 [价值保存结构理论](docs/structural-theory-value-preservation-llm-systems.zh-CN.md)。

## 一个直观判断

如果你让模型"再深入一点""再有洞察一点""再具体一点"，它确实变好了，但每一版都像在同一个方向上打磨，那么问题很可能不在生成质量，而在任务形态。

这时更好的问题不是：

```text
怎样让模型再写好一点？
```

而是：

```text
这个任务真正缺的控制变量是什么？
```

它可能需要状态观察、缺通道变量的测量、工具验证、检索证据、构造反例、生成评分规约、换成决策矩阵、列出失败模式，或者让人补一个偏好、授权、边界或责任判断。

一个有用的检查是：什么对象会改变下一次生成？

- 状态矩阵：把隐藏假设变成显式情境。
- 测量或原始信号请求：把缺失通道变量转进表征。
- 评分规约：把模糊质量变成可检查标准。
- 失败模式清单：暴露一个看似合理的答案会怎样失败。
- 查询计划：把缺失事实从想象转移到检索。
- 最小充分人类问题（Minimal Sufficient Human Query / MSHQ）：隔离出价值、权限或责任变量。

## 理解之后能少走哪些弯路

:::cards
### 别在错误抽象上反复打磨

如果模型一开始就把任务理解错了，风格越好越危险。先把目标、变量、约束、状态和成功条件弄清楚。

### 别把缺状态或缺通道误判成缺智能

如果正确答案依赖现实状态，或依赖一个当前表征里没有的变量，就应该补充观察、测量、读取文件、运行测试、查证来源、检查日志，或提出一个最小充分人类问题。

### 别用投票放大默认答案

当最优答案本来就少见时，多数一致并不可靠。你需要尾部搜索、扰动、反例、检索或结构化验证。
:::

### 别让人重新接回整个任务

如果缺失变量确实由人类治理，正确动作也不是"请你重做一遍"。正确动作是一个小问题：确认事实、选择优先级、授权边界、验证假设，或定义停止标准。这一类最小问题被本项目称为 **最小充分人类问题**，它来自 [治理式人机协作](docs/governed-human-ai-collaboration.zh-CN.md) 与 [人类协助型操作失配](docs/human-assist-operational-mismatches.zh-CN.md) 的工作稿。

### 别在等待期间让 agent 干等

升级给人之后，长程 agent 仍可以做大量可逆的准备工作：候选矩阵、低成本实验、风格轴、对比样例、查询计划、依赖图、回滚路径。这些动作构成"等待期间的自治"，也正是 [状态治理智能体范式（State-Governed Agent Regime / SGAR）](docs/state-governed-agent-regime-for-governed-llm-systems.zh-CN.md) 所强调的"等待期间继续推进可逆工作"。

## 为什么它会成为很多高价值工作的共同基础

今后绝大部分高价值工作，都会或多或少与对抗 LLM 平庸有关。原因不是一句"AI 很重要"这么简单，而是整个信息处理逻辑已经变了。

::::cards
### AI 已经变成默认的信息处理引擎

AI 正在重构信息处理的基本方式：检索、压缩、比较、起草、组合、分析、生成候选、调用工具，都会越来越多地先经过 AI。大量不围绕 AI 组织信息处理的工作，会迅速贬值、边缘化，甚至直接消失。

这意味着，只要一个工作开始把 AI 当作信息引擎，它迟早就要面对同一个问题：如何不被模型的默认续写路径拖向流畅但平庸的答案。换句话说，**只要你用 AI 处理信息，你就迟早要和自回归引力打交道。**

### 能被 LLM 卓越处理的部分会迅速自动化

凡是已经落在 LLM 卓越区间里的任务，通常都会很快被产品化、流水线化和自动化。因为在这类任务里，模型的局部生成倾向和任务价值方向本来就是一致的，人类只需要提供很少的额外治理。

因此，未来仍然需要大量人类参与的部分，往往不是那些 AI 已经能流畅完成的部分，而是那些**模型局部看起来很会做，但全局上仍然做不对、做不稳、选不准**的部分。也就是说，仍然值钱、仍然需要判断、仍然需要组织的工作，大多会落在 LLM 平庸附近。

### 高价值任务天然更容易落在 LLM 平庸区

科研、金融、战略、创意、复杂产品决策、组织治理，这些任务之所以值钱，往往正是因为它们依赖隐藏状态、长程依赖、真实约束、尾部机会、验证难度和价值判断。

这些因素恰好都是 LLM 最容易失真的地方。一个任务越高价值，越不只是"把常见模式说得更好"；它通常越依赖：

- 稀有但关键的结构
- 不能被局部润色替代的全局判断
- 不能只靠流畅感判断的真实验证
- 不能被默认分布覆盖的人类偏好、授权和责任边界

这也是为什么，一旦某类高价值任务真的被 LLM 稳定地处理成了 LLM 卓越，它很快就会失去原本的稀缺性，变得更便宜、更标准化，甚至不再值得由人专门做。真正持续值钱的部分，会不断往"模型还不能靠默认生成稳定拿下"的区域移动。
::::

所以，理解 LLM 平庸不是一个只对提示词工程师有用的小技巧，而是很多工作的共同基础。你不一定每天都在研究模型，但你越来越需要知道：

- LLM 平庸通常长什么样
- 它为什么会出现
- 哪些任务天然更容易落进去
- 可以用什么方式去对抗它

:::takeaway
因为对抗 LLM 平庸，正在变成很多高价值工作的底层能力：不是某个行业的附加技能，而是跨科研、金融、创意、产品和治理工作的共同基础。
:::

## 这套框架解决什么

它提供的不是一个万能提示，而是一种判断方式：先看任务处在哪个对齐区间，再决定要不要直接生成、是否需要构造中间对象、何时引入工具验证，以及什么时候应该让人裁决缺失变量。

乐观之处在于，目标不是让模型少生成，而是让生成处在正确的任务形态里：概率与价值对齐的地方直接生成；局部流畅不再可靠的边界，则通过控制对象、验证和人类变量来治理。
