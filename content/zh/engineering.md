## 明天就可以改的一件事

在要求模型“再给一版最终答案”之前，先问：

```text
什么中间对象会改变这个任务的形状？
```

这个中间对象可能是状态矩阵、rubric、依赖图、失败模式清单、边界情况集合、查询计划、任务模型、结构提纲、验证清单或候选约束。很多时候，LLM 更擅长先生成这些对象；而这些对象一旦稳定，最后的写作、扩写、格式化和语气调整就会进入更接近自回归卓越的区间。

## 从平庸到卓越的转化

所谓治理，不是把模型绑死，而是改变模型面对的任务。

直接生成通常是：

```text
输入 → 最终答案
```

高错配任务更适合改成：

```text
输入 → 任务模型 → 控制对象 → 验证/削弱 → 最终表达
```

这样做的目的，是把原本很难直接生成的高价值答案，拆成一组更容易生成和检查的中间任务：压缩上下文、枚举状态、生成 rubric、构造反例、列失败模式、写查询、建立依赖图，再从这些受控对象渲染最终输出。

## Knowledge Governance 是什么

Knowledge Governance 是推理阶段的控制层。它把“最终表达”与“任务特定控制知识的获取和管理”分开。

它关心的不是把 prompt 写得更长，而是让关键知识具有生命周期：

:::cards
### 可见

重要假设、边界、偏好、约束和失败条件要从流畅文本里拿出来，成为可以检查的对象。

### 可验证

候选规则不能只因为听起来合理就生效。它需要样例、测试、工具结果、专家判断、反例或环境反馈来支持。

### 可撤销

一条规则只在某些条件下成立。状态、版本、权限、目标或证据变化时，它应该被削弱、替换或撤销。
:::

## GKO 在实践中长什么样

Governed Knowledge Object（GKO）保存的是 AI 应该知道、遵守或检查的控制知识。一个有用的 GKO 至少要回答：

:::cards
### 适用条件

这条知识在什么情况下才成立？不要让局部有效的规则悄悄变成全局真理。

### 证据强度

它来自一个例子、多次失败、测试结果、工具运行、统计证据，还是专家确认？

### 优先级与撤销

规则冲突时谁优先？什么观察会削弱它、覆盖它，或让它失效？
:::

一个外部沟通场景里的 GKO 可以是：

```json
{
  "condition": "外部沟通涉及退款、价格、交付日期或法律承诺",
  "assertion": "不得直接承诺；必须先获得授权，或改为准备草稿",
  "strength": "objective-grounded",
  "priority": 0.95,
  "lifespan": "project",
  "revocation_trigger": "授权人授予该类承诺的长期权限",
  "evidence": "外部承诺具有声誉、财务和法律风险",
  "source": "authority governance"
}
```

## 一个可执行循环

1. 判断任务是否已经处于自回归卓越区间：如果只是压缩、改写、格式转换或常规候选生成，直接生成即可。
2. 诊断 mismatch profile：聚合、支撑、状态、规约，哪一种最强？
3. 构造任务模型：真实成功条件、目标承载者、约束、噪声、隐藏假设和评价标准。
4. 构造控制空间：状态矩阵、依赖图、rubric、失败模式、边界情况、查询计划或验证清单。
5. 生成候选 GKO：从证据、失败、扰动、对比样例和工具结果中提炼控制规则。
6. 验证或削弱 GKO：区分已验证规则、局部规则、待确认假设和应拒绝声明。
7. 从受治理知识渲染最终输出，并检查输出是否保留了控制对象。
8. 监控失败，把新的证据写回 GKO，必要时降级或撤销旧规则。

## 工程判断

治理有成本。不是所有任务都需要完整控制层。越是低风险、低错配、强验证、强模式化的任务，越适合轻量直接生成；越是高风险、高错配、强隐含目标、需要复用判断的任务，越应该把控制知识外化。

好的工程系统不是让模型少生成，而是让模型在正确的任务形态里生成。
