## 先问一个反过来的问题

模型还在持续迭代，能力也还在往上走。于是很容易得出一个判断：今天解决不了的问题，也许再等一轮训练、下一代模型，或者再来一次 scaling，就会自己消失。

但更值得反过来问一句：**模型训练迭代，真的能解决所有重要问题吗？** 如果不能，眼前的问题就不只是"现在还不够强"，而是某些任务从一开始就被 LLM 的算法和架构特征卡住了上限。

日常使用里，这种情况并不少见：同一个模型在一些任务上很好用，在另一些任务上却总差最后一截。你补背景、定格式、加约束，让它反思，再多给几个版本。答案确实会更完整、更流畅，也更像那么回事，但真正决定成败的那一步还是没有出现。

这不只是"模型不够聪明"，也不只是"提示词还没写好"。因为同一个模型在别的任务上明明很能打：它会压缩上下文、改写文本、生成结构、展开候选方案、解释代码、调用工具、辅助验证。问题在于，**模型的局部能力，并不会自动变成你真正想要的任务价值**。

这就是本项目所说的 **[LLM 平庸](/zh/glossary#llm-mediocrity)**：在某些任务里，语言概率系统和真实问题域之间存在结构性失配。模型会沿着统计上自然、容易续写、支持度更高，也更容易被接受的方向前进；可真实价值往往取决于全局结构、隐藏状态、更明确的规格，或者低支持区域里的稀缺解法。**也就是说，有些失败不是继续训练就一定会消失，而是已经碰到了结构性天花板。**

所以，对抗 LLM 平庸，关键不在于没完没了地改 prompt，而在于先做诊断：任务里哪些部分已经和模型的生成倾向对齐，哪些部分只是[局部对齐](/zh/glossary#local-alignment)，又有哪些部分必须靠控制空间、验证、工具、人类裁决或硬状态治理来修复。

认识并对抗这种平庸，很可能会成为 AI 使用者最常碰到的任务之一。目标不是压住模型的生成能力，而是保留它真正擅长的部分，同时别让局部流畅冒充全局价值。

整站就是顺着这条链路往下展开的。先说明为什么有些问题不能只靠等模型变强来解决，再解释概率和价值为什么会错开，然后用[六类原始失配](/zh/glossary#six-primitive-mismatches)定位真正卡住的部分。接着用治理对象体系（[GKO](/zh/glossary#gko) / [GExO](/zh/glossary#gexo) / [GEsO](/zh/glossary#geso) / [MSHQ](/zh/glossary#mshq)）和状态治理智能体范式（[SGAR](/zh/glossary#sgar)），把问题改写成可搜索、可验证、可复用的工程对象。最后再用[审计工程](/zh/glossary#audit-engineering)和经验回写，让下一轮任务比这一轮更稳。这不是一组松散文章，而是一条从结构判断走到工程交付的完整链路。

> **说明**
>
> 这套框架首先来自工程实践与工程直觉的总结。它更看重能否帮助人重新组织任务、提高工程收益，而不是提供数学上完备的最终理论；理论部分更像一种会随着实践反馈继续调整的思维脚手架。

## 一句话地图

这个项目把 LLM 任务分成三个区间：

:::cards
### LLM 平庸
Tag: 概率与价值错位

LLM 给出的答案在某些时候未必是高价值高质量的，可能是很平庸的答复，而非你期望的答案。

### 局部对齐
Tag: 最常见的现实区间

对于一个复杂问题，LLM 擅长处理其中的一部分，但是另外一部分给出的答案是平庸且无价值的。

### LLM 卓越
Tag: 概率与价值同向

模型擅长处理此类问题，给出的答案往往就是你期待和需要的。
:::

最常见的是中间区间。产品备忘录、代码审查、客服回复或研究综述，往往同时包含模型容易处理的部分，也包含依赖隐藏状态、全局协调、稀缺证据或价值选择的部分。关键不是"要不要用 AI"，而是找出对齐边界在哪里，并把不对齐的部分转化成更低失配的中间任务。

## 从流畅草稿走向真正有价值的答案

如果你想看的不是“六类失配如何定义”，而是“这些概念最早是怎么在真实工程挫败里被逼出来的”，可以先读 [六类原始失配的工程来源](/docs/engineering-origins-of-six-primitive-mismatches.zh-CN.md)。那篇文档更像一份发现日志：从大规模量化采样、对抗自回归引力，到故事生成、金融任务与日常复杂问题中的一路修正。

假设你让模型写一份战略建议。它很快就交出一份漂亮的备忘录，但真正该选哪种方案，取决于一个从来没说清楚的预算上限。这时再让模型"优化一下"，通常只会让文字更完整，不会让缺失的预算自己冒出来。

更有效的做法，是先别碰最终文本，转而回答几个更窄的问题：

1. **当前处在哪个区间？** 模型处在局部对齐区间：它擅长写作和比较方案，但直接生成不能保证推荐正确。
2. **为什么局部质量不能继续预测成功？** 这里主要存在状态失配与规格失配：预算状态未知，主导取舍也没有明确。
3. **再次写作前，什么结构必须先显式化？** 构造一张包含成本、速度、风险和预期回报的选项矩阵。
4. **哪些变量仍不能由模型自己补足？** 先验证矩阵里的事实估计，再让人确认预算上限和主导目标。
5. **变量解决后，模型应该做什么？** 从已验证的选项矩阵和已确认的取舍中，生成最终备忘录。

这组问题形成了本项目从诊断走向交付的链条：

```text
识别概率与价值的关系区间
-> 用六类原始失配诊断卡住的部分
-> 把不对齐的部分转化成治理对象（GKO / GExO / GEsO / MSHQ）
-> 在硬状态体制（SGAR）里执行、验证、提交状态转移
-> 用审计工程把失败信号写回控制增量
-> 从受治理状态生成最终答案
```

这条链里的每一个箭头，都在改写模型眼前的任务。它不是每个请求都必须照着走一遍的固定流程，它的作用更像一个提醒：当真正瓶颈还在上游时，别把时间继续花在润色最终答案上。

### 六类原始失配（来自价值保存结构理论）

六类原始失配用于诊断链条中的第二步：为什么普通输出空间搜索会卡住。完整定义见 [六类原始失配总览](/docs/six-primitive-mismatches-pipeline-derived-taxonomy-llm-systems.zh-CN.md)，结构推导见 [价值保存结构理论](/docs/structural-theory-value-preservation-llm-systems.zh-CN.md)。

::::cards
### Aggregation：聚合失配

局部改进不一定累积成全局价值。战略方案可以读起来很完整，却没有抓住主导取舍；代码模块可以各自合理，却破坏依赖顺序。

### Support：支持失配

真正有价值的答案在当前模型、搜索方式和预算下很难到达。缺失的可能是少见框架、低显著性证据或非显然的失败模式。

### State：状态失配

正确答案依赖隐藏或变化中的状态：市场环境、生产环境、用户情绪、权限边界、时间窗口或政策语境。

### Specification：规格失配

系统可优化的代理目标偏离了真实目标。输出满足提示、风格或评分规约，却没有满足用户真正的成功条件。

### Fitting Boundary：拟合边界失配

模型过度绑定局部证据链、代理指标、角色模板或反馈信号。答案在一个场景里看似合理，但换到相邻场景、审计协议、机制或偏好后就失效。

### Observation-Representation：观测-表征失配

决定性世界变量没有进入模型可访问表征。系统需要测量、原始证据、工具反馈、更丰富模态、日志、测试或结构化控制对象，推理才有资格闭合。
::::

## 什么人适合这个项目

这个项目适合那些已经频繁使用 LLM，但开始觉得"只是会用提示词"不够的人。

如果你遇到过这些情况，这里可能对你有用：

- 你发现模型能写出流畅答案，但关键判断仍然不可靠。
- 你在写作、研究、代码、投资、产品或协作任务里，反复遇到"看起来对，但就是不够好"的输出。
- 你不满足于 prompt 技巧，而想理解任务为什么会和模型生成倾向错开。
- 你正在构建 agent、workflow、评估器、知识库或自动化系统，需要把 LLM 放进可验证、可回滚、可治理的流程里。
- 你关心人和 AI 如何协作：哪些事情该交给模型，哪些变量必须由人来治理。

这个项目不假设读者是 AI 研究员。它更关心真实任务里的工程经验：如何识别失配、构造中间对象、设计验证环节，并让模型的局部能力真正转化成任务价值。

## 如何对抗 LLM 平庸

核心原则是：**保留模型已经擅长的部分，把不对齐的部分转化成更容易生成、验证和治理的任务形态。**

:::cards
### 不在最终答案空间里硬搜

困难任务不要一上来就要求"直接给最终答案"。先生成状态矩阵、评分规约、依赖图、失败模式、候选方案、查询计划或结构化提纲，让模型面对更低失配的子任务。

### 把控制知识外化

真正重要的假设、约束、边界、偏好和撤销条件，不应该埋在一段流畅文本里。它们应该变成可检查、可复用、可削弱或撤销的受治理知识对象（Governed Knowledge Object, GKO）。

### 让人治理缺失变量

人不应只是给 AI 草稿做校对。人的角色是设定价值、选择权重、授权风险、提供真实状态、判断品味，并承担责任。好的 AI agent 应该用最小充分人类问题（Minimal Sufficient Human Query, MSHQ）来问，而不是把整个任务交还给人。

### 让长程行动落在硬状态上

对于需要长期推进的 agent，计划、工具调用、观测、验证、人类回答和审计发现都应该进入外部硬状态，而不是只停留在聊天上下文。状态治理型 Agent 体制（SGAR）让"完成"必须经过证据与验证，而不是被自我叙事宣称为完成。
:::

实践上，困难任务通常不应该直接进入最终文本，而应先经过一组中间对象：

```text
输入 -> 任务模型 -> 控制对象（GKO / GEsO / MSHQ） -> 硬状态（SGAR） -> 验证 / 审计 -> 最终答案
```

这些对象不是为了增加流程感，而是把高失配的最终输出问题，转化成更小、更容易让模型发挥局部优势的操作。审计工程（[Audit Engineering](/docs/audit-engineering-failure-localization-control-space-writeback.zh-CN.md)）则把每一次失败信号结构化为控制增量，让下一轮搜索不至于重复犯同样的错。若想把这条运行时链路进一步放到可量化框架里看，可以继续读 [Agent Hardness Framework](/docs/agent-hardness-framework.zh-CN.md)。

## 这个项目接下来会做什么

- **公共解释层**：让不读论文的人也能理解 LLM 平庸、局部对齐和 LLM 卓越。
- **理论层**：展开六类原始失配、知识治理、GKO / GExO / GEsO / MSHQ、SGAR、审计工程，以及它们在运行时中的可量化关系，详见 [价值保存结构理论](/docs/structural-theory-value-preservation-llm-systems.zh-CN.md)、[受治理 LLM 对象模型与接口规范](/docs/governed-llm-object-model-interface-specification.zh-CN.md) 与 [Agent Hardness Framework](/docs/agent-hardness-framework.zh-CN.md)。
- **工程层**：沉淀工具与模板，把控制对象、硬状态 ledger、验证循环和最小人类接入点落到真实任务中。
- **协作层**：把人从普通处理者上移为价值、权限、品味、预算、证据和责任的治理者，详见 [治理式人机协作](/docs/governed-human-ai-collaboration.zh-CN.md) 与 [人类协助型操作失配](/docs/human-assist-operational-mismatches.zh-CN.md)。

## 欢迎贡献

这个项目欢迎贡献案例、批评和改进建议。

特别欢迎这些类型的贡献：

- **真实任务案例**：哪些任务里 LLM 表面表现很好，但最终价值不稳定。
- **工程模式**：你如何把任务拆成控制对象、验证对象、评分规约或人类决策点。
- **失败样本**：哪些 prompt、agent 或 workflow 看起来合理，但最后被证明不可控。
- **概念修正**：对"LLM 平庸""局部对齐""失配""控制空间""GKO / GExO / GEsO / MSHQ""SGAR""审计工程"等概念的反例、补充或更清晰表达。
- **工具实现**：能把这些治理动作落到代码、模板、评估器或工作流里的最小组件。

贡献不需要一开始就完整。一个具体失败案例、一段可复现流程、一个更准确的术语，或者一次有证据的反驳，都比泛泛而谈更有价值。
