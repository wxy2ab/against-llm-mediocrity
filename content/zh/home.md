## 从一个最常见的挫败开始

我们越来越多地依赖 LLM 帮我们完成任务：写代码、做研究、分析材料、制定方案、整理知识、辅助决策。有些任务完成得很好，甚至好到让人觉得“这件事以后就应该交给 AI”。但也有些任务不太理想。于是你开始优化提示词：补充背景、明确格式、增加约束、要求它反思、让它多给几个版本。

有时候这很有效。但最终你会遇到一些任务：提示词已经优化了很多次，结果仍然不理想。答案越来越完整，表达越来越顺，结构越来越像那么回事，但真正想要的东西还是没有出来。它像被关在一只看不见的笼子里，你能感觉到目标就在附近，却怎么也释放不出来。

这不是简单的“模型不够聪明”，也不只是“提示词还没写好”。因为同一个模型在另一些任务上明明表现很好：它能压缩上下文、改写文本、生成结构、展开候选方案、解释代码、调用工具、辅助验证。真正的问题是，模型的局部能力并不总能自动转化成你要的任务价值。

这就是本项目所说的 **LLM 平庸**：在某些任务里，语言概率系统和真实问题域之间存在结构性失配。模型会沿着统计上自然、容易续写、支持更高或更容易被接受的方向前进，但真实价值可能取决于全局结构、隐藏状态、更清晰的规格，或低支持区域里的稀缺结构。

所以，对抗 LLM 平庸的关键不是无止境地继续改提示词，而是先判断：这个任务的哪些部分已经和模型的生成倾向对齐，哪些部分只是局部对齐，哪些部分必须通过控制空间、验证、工具或人类裁决来治理。

认识并对抗这种平庸，可能是 AI 使用者最常面对的任务。实践目标不是压制模型的生成能力，而是保留它真正擅长的部分，同时防止局部流畅伪装成全局价值。

整站的读法也按这个顺序展开：先从这种常见挫败出发，引出概率与价值为什么会错开，再把错开的部分改写成控制空间、验证对象和最小人类问题。换句话说，这不是一组松散文章，而是一条从场景到诊断、再到交付的链路。

## 一句话地图

这个项目把 LLM 任务分成三个区间：

:::cards
### LLM 平庸
Tag: 概率与价值错位

模型容易生成的答案，和任务真正有价值的答案不在同一个区域。多轮润色可能提高表面质量，却没有触及真正的瓶颈。

### 局部对齐
Tag: 最常见的现实区间

模型能做好很多局部操作，比如压缩、改写、列举、比较、生成结构，但这些局部成功未必能自动组合成全局成功。

### LLM卓越
Tag: 概率与价值同向

当局部续写倾向稳定指向任务价值时，自回归不是问题，而是优势。上下文压缩、语义扩写、结构化转换和语体迁移常常属于这一区间。
:::

最常见的是中间区间。产品备忘录、代码审查、客服回复或研究综述，往往同时包含模型容易处理的部分，也包含隐藏状态、全局协调、稀缺证据或价值选择。关键不是“要不要用 AI”，而是找出对齐边界在哪里。

## 从流畅草稿走向真正有价值的答案

假设你让模型给出一份战略建议。模型很快写出了一份漂亮的备忘录，但真正应该选择哪种方案，取决于一个从未说明的预算上限。此时要求模型“再优化一下”，通常只会让文字更完整，并不会让缺失预算自动出现。

更有效的做法，是暂时停止修改最终文本，依次回答几个更窄的问题：

1. **当前处在哪个区间？** 模型处在局部对齐区间：它擅长写作和比较方案，但直接生成不能保证推荐正确。
2. **为什么局部质量不能继续预测成功？** 这里主要存在状态与规格失配：预算状态未知，主导取舍也没有明确。
3. **再次写作前，什么结构必须先显式化？** 构造一张包含成本、速度、风险和预期回报的选项矩阵。
4. **哪些变量仍不能由模型自己补足？** 先验证矩阵中的事实估计，再让人确认预算上限和主导目标。
5. **变量解决后，模型应该做什么？** 从已验证的选项矩阵和已确认的取舍中，生成最终备忘录。

这组问题形成了本项目从诊断走向交付的链条：

```text
识别概率与价值的关系区间
-> 诊断阻止全局价值的失配
-> 构造暴露缺失结构的中间对象
-> 验证证据，或获得人类治理变量
-> 从受治理状态生成最终答案
```

每一个箭头都在改变模型正在解决的任务。这条链不是每个请求都必须执行的固定流程；它的作用是避免在真正瓶颈位于上游时，仍然反复润色最终答案。

五类原始失配（primitive mismatches）用于诊断链条中的第二步：

::::cards
### Aggregation：聚合失配

局部改进不一定累积成全局价值。战略方案可以读起来很完整，却没有抓住主导取舍；代码模块可以各自合理，却破坏依赖顺序。

### Support：支持失配

真正有价值的答案在当前模型、搜索方式和预算下很难到达。缺失的可能是少见框架、低显著性证据或非显然失败模式。

### State：状态失配

正确答案依赖隐藏或变化中的状态：市场环境、生产环境、用户情绪、权限边界、时间窗口或政策语境。

### Specification：规格失配

系统可优化的代理目标偏离真实目标。输出满足提示、风格或评分规约，却没有满足用户真正的成功条件。

### Fitting Boundary：拟合边界失配

模型过度绑定局部证据链、代理指标、角色模板或反馈信号。答案在一个场景里看似合理，但换到相邻场景、审计协议、机制或偏好后就失效。
::::

## 什么人适合这个项目

这个项目适合那些已经频繁使用 LLM，但开始感觉“只是会用提示词”不够的人。

如果你遇到过这些情况，这里可能对你有用：

- 你发现模型能写出流畅答案，但关键判断仍然不可靠。
- 你在写作、研究、代码、投资、产品或协作任务里，反复遇到“看起来对，但就是不够好”的输出。
- 你不满足于 prompt 技巧，而想理解任务为什么会和模型生成倾向错开。
- 你正在构建 agent、workflow、评估器、知识库或自动化系统，需要把 LLM 放进可验证、可回滚、可治理的流程里。
- 你关心人和 AI 如何协作：哪些事情该交给模型，哪些变量必须由人来治理。

这个项目不假设读者是 AI 研究员。它更关心真实任务里的工程经验：如何识别失配、构造中间对象、设计验证环节，并让模型的局部能力真正转化成任务价值。

## 如何对抗 LLM 平庸

核心原则是：**保留模型已经擅长的部分，把不对齐的部分转化成更容易生成、验证和治理的任务形态。**

:::cards
### 不在最终答案空间里硬搜

困难任务不要一上来就要求“直接给最终答案”。先生成状态矩阵、评分规约、依赖图、失败模式、候选方案、查询计划或结构化提纲，让模型面对更低失配的子任务。

### 把控制知识外化

真正重要的假设、约束、边界、偏好和撤销条件，不应该埋在一段流畅文本里。它们应该变成可检查、可复用、可削弱或撤销的受治理知识对象（Governed Knowledge Object, GKO）。

### 让人治理缺失变量

人不应只是给 AI 草稿做校对。人的角色是设定价值、选择权重、授权风险、提供真实状态、判断品味，并承担责任。好的 AI agent，也就是能自主调用工具并推进任务的 AI 系统，应该问最小充分问题，而不是把整个任务交还给人。
:::

实践上，困难任务通常不应该直接进入最终文本，而应先经过一组中间对象：

```text
输入 -> 任务模型 -> 控制对象 -> 验证 / 升级 -> 最终答案
```

这些对象可以是评分规约（rubric）、状态矩阵、依赖图、候选集、失败模式清单、验证清单、GKO、受治理升级对象（Governed Escalation Object, GEO）或最小充分人类问题（Minimal Sufficient Human Query, MSHQ）。它们不是为了增加流程感，而是把高失配的最终输出问题，转化成更小、更容易让模型发挥局部优势的操作。

## 这个项目接下来会做什么

- 公共解释层：让不读论文的人也能理解 LLM 平庸、局部对齐和LLM卓越。
- 理论层：展开五类原始失配、知识治理、GKO/GEO 和治理循环。
- 工程层：沉淀工具与模板，把控制对象、验证循环和最小人类接入点落到真实任务中。
- 协作层：把人从普通处理者上移为价值、权限、品味、预算、证据和责任的治理者。

## 欢迎贡献

这个项目欢迎贡献案例、批评和改进建议。

特别欢迎这些类型的贡献：

- 真实任务案例：哪些任务里 LLM 表面表现很好，但最终价值不稳定。
- 工程模式：你如何把任务拆成控制对象、验证对象、评分规约或人类决策点。
- 失败样本：哪些 prompt、agent 或 workflow 看起来合理，但最后被证明不可控。
- 概念修正：对“LLM 平庸”“局部对齐”“失配”“控制空间”等概念的反例、补充或更清晰表达。
- 工具实现：能把这些治理动作落到代码、模板、评估器或工作流里的最小组件。

贡献不需要一开始就完整。一个具体失败案例、一段可复现流程、一个更准确的术语，或者一次有证据的反驳，都比泛泛而谈更有价值。
