## 先问一个反过来的问题

模型还在持续迭代，能力也还在往上走。于是很容易得出一个判断：今天解决不了的问题，也许再等一轮训练、下一代模型，或者再来一次 scaling，就会自己消失。

但更值得反过来问一句：**模型训练迭代，真的能解决所有重要问题吗？** 如果不能，眼前的问题就不只是“现在还不够强”，而是某些任务从一开始就被 LLM 的算法和架构特征卡住了上限。

日常使用里，这种情况并不少见：同一个模型在一些任务上很好用，在另一些任务上却总差最后一截。你补背景、定格式、加约束，让它反思，再多给几个版本。答案确实会更完整、更流畅，也更像那么回事，但真正决定成败的那一步还是没有出现。

原因不只是“模型不够聪明”，也不只是“提示词还没写好”。同一个模型在别的任务上明明很能打：它会压缩上下文、改写文本、生成结构、展开候选方案、解释代码、调用工具、辅助验证。问题在于，**模型的局部能力，并不会自动变成你真正想要的任务价值**。

这就是本项目所说的 **[LLM 平庸](/zh/glossary#llm-mediocrity)**：在某些任务里，语言概率系统和真实问题域之间存在结构性失配。模型会沿着统计上自然、容易续写、支持度更高，也更容易被接受的方向前进；可真实价值往往取决于全局结构、隐藏状态、更明确的规格，或者低支持区域里的稀缺解法。**也就是说，有些失败不会因为继续训练就一定消失，它们已经碰到了结构性天花板。**

所以，对抗 LLM 平庸，关键不在于没完没了地改 prompt，而在于先做诊断：任务里哪些部分已经和模型的生成倾向对齐，哪些部分只是[局部对齐](/zh/glossary#local-alignment)，又有哪些部分必须靠控制空间、验证、工具、人类裁决或硬状态治理来修复。

认识并对抗这种平庸，很可能会成为 AI 使用者最常碰到的任务之一。目标不是压住模型的生成能力，而是保留它真正擅长的部分，同时别让局部流畅冒充全局价值。

整站就是顺着这条链路展开的。先说明为什么有些问题不能只靠等模型变强来解决，再解释概率和价值为什么会错开，然后用[六类原始失配](/zh/glossary#six-primitive-mismatches)定位真正卡住的部分。接着登场的是一组治理对象——受治理的知识对象、执行对象、升级对象（[GKO](/zh/glossary#gko) / [GExO](/zh/glossary#gexo) / [GEsO](/zh/glossary#geso)）和最小充分人类问题（[MSHQ](/zh/glossary#mshq)）——以及状态治理智能体范式（[SGAR](/zh/glossary#sgar)）。它们把问题改写成可搜索、可验证、可复用的工程对象。最后再用[审计工程](/zh/glossary#audit-engineering)和经验回写，让下一轮任务比这一轮更稳。这些页面不是一组松散的文章，而是一条从结构判断走到工程交付的完整链路。

> **说明**
>
> 这套框架首先是对工程实践与工程直觉的总结。它更看重能不能帮人重新组织任务、提高工程收益，而不是给出一套数学上完备的最终理论。理论部分更像思维脚手架，会随着实践反馈继续调整。

## 一句话地图

这个项目把 LLM 任务分成三个区间：

:::cards
### LLM 平庸
Tag: 概率与价值错位

LLM 给出的答案在某些时候未必是高价值高质量的，可能是很平庸的答复，而非你期望的答案。

### 局部对齐
Tag: 最常见的现实区间

对于一个复杂问题，LLM 擅长处理其中的一部分，但是另外一部分给出的答案是平庸且无价值的。

### LLM 卓越
Tag: 概率与价值同向

模型擅长处理此类问题，给出的答案往往就是你期待和需要的。
:::

最常见的是中间这个区间。产品备忘录、代码审查、客服回复或研究综述里，往往既有模型容易处理的部分，也有依赖隐藏状态、全局协调、稀缺证据或价值选择的部分。关键不是“要不要用 AI”，而是找出对齐边界在哪里，并把不对齐的部分转化成失配更低的中间任务。

## 从流畅草稿走向真正有价值的答案

假设你让模型写一份战略建议。它很快交出一份漂亮的备忘录，但真正该选哪种方案，取决于一个从来没说清楚的预算上限。这时再让模型“优化一下”，通常只会让文字更完整，不会让缺失的预算自己冒出来。

更有效的做法是先别碰最终文本，转而回答几个更窄的问题：

1. **当前处在哪个区间？** 模型处在局部对齐区间：它擅长写作和比较方案，但直接生成不能保证推荐正确。
2. **为什么局部质量不再能预测成功？** 主要原因是状态失配与规格失配：预算状态未知，主导取舍也没有明确。
3. **重新动笔之前，哪些结构必须先显式写出来？** 构造一张选项矩阵，列出成本、速度、风险和预期回报。
4. **哪些变量模型自己仍然补不上？** 先验证矩阵里的事实估计，再请人确认预算上限和主导目标。
5. **变量确定之后，模型该做什么？** 根据已验证的选项矩阵和已确认的取舍，生成最终备忘录。

把这组问题完整展开，就是本项目从诊断走到交付的链条：

```text
识别概率与价值的关系区间
-> 用六类原始失配诊断卡住的部分
-> 把不对齐的部分转化成治理对象（GKO / GExO / GEsO / MSHQ）
-> 在 SGAR 的硬状态里执行、验证并提交状态转移
-> 用审计工程把失败信号写回成控制增量
-> 从受治理状态生成最终答案
```

这条链上的每一个箭头，都在改写模型眼前的任务。它不是每个请求都必须照着走一遍的固定流程，更像一个提醒：真正的瓶颈还在上游时，别再把时间花在润色最终答案上。

### 六类原始失配（来自价值保存结构理论）

六类原始失配用在链条的第二步：诊断普通的输出空间搜索为什么会卡住。完整定义见 [六类原始失配总览](/docs/six-primitive-mismatches-pipeline-derived-taxonomy-llm-systems.zh-CN.md)，结构推导见 [价值保存结构理论](/docs/structural-theory-value-preservation-llm-systems.zh-CN.md)。

::::cards
### Aggregation：聚合失配

局部改进不一定累积成全局价值。战略方案可以读起来很完整，却没有抓住主导取舍；代码模块可以各自合理，却破坏依赖顺序。

### Support：支持失配

在当前模型、搜索方式和预算下，真正有价值的答案很难到达。缺的可能是少见的框架、显著性低的证据，或者不容易想到的失败模式。

### State：状态失配

正确答案依赖隐藏或变化中的状态：市场环境、生产环境、用户情绪、权限边界、时间窗口或政策语境。

### Specification：规格失配

系统能够优化的代理目标偏离了真实目标。输出满足了提示、风格或评分规约，却没有满足用户真正的成功条件。

### Fitting Boundary：拟合边界失配

模型过度绑定局部证据链、代理指标、角色模板或反馈信号。答案在一个场景里看似合理，一旦换成相邻的场景、审计协议、机制或偏好就失效。

### Observation-Representation：观测-表征失配

起决定作用的世界变量没有进入模型能访问到的表征。系统要先补上测量、原始证据、工具反馈、更丰富的模态、日志、测试或结构化控制对象，推理才有条件闭合。
::::

如果你想看的不是“六类失配如何定义”，而是“这些概念最早是怎么在真实工程挫败里被逼出来的”，可以读 [六类原始失配的工程来源](/docs/engineering-origins-of-six-primitive-mismatches.zh-CN.md)。那篇文档更像一份发现日志：从大规模量化采样、对抗自回归引力，到故事生成、金融任务与日常复杂问题中的一路修正。

## 什么人适合这个项目

这个项目适合已经频繁使用 LLM、但开始觉得“只会写提示词”还不够的人。

如果你遇到过这些情况，这里可能对你有用：

- 你发现模型能写出流畅的答案，但关键判断仍然不可靠。
- 你在写作、研究、代码、投资、产品或协作任务里，反复遇到“看起来对，但就是不够好”的输出。
- 你不满足于 prompt 技巧，想弄清任务为什么会和模型的生成倾向错开。
- 你正在构建 agent、workflow、评估器、知识库或自动化系统，需要把 LLM 放进可验证、可回滚、可治理的流程里。
- 你关心人和 AI 如何协作：哪些事情该交给模型，哪些变量必须由人来治理。

这个项目不假设读者是 AI 研究员。它更关心真实任务里的工程经验：如何识别失配、构造中间对象、设计验证环节，并让模型的局部能力真正转化成任务价值。

## 如何对抗 LLM 平庸

核心原则是：**保留模型已经擅长的部分，把不对齐的部分转化成更容易生成、验证和治理的任务形态。**

:::cards
### 不在最终答案空间里硬搜

遇到困难任务，不要一上来就要求“直接给最终答案”。先生成状态矩阵、评分规约、依赖图、失败模式、候选方案、查询计划或结构化提纲，让模型面对失配更低的子任务。

### 把控制知识外化

真正重要的假设、约束、边界、偏好和撤销条件，不该埋在一段流畅的文本里。它们应该变成可检查、可复用、可削弱、可撤销的受治理知识对象（Governed Knowledge Object, GKO）。

### 让人治理缺失变量

人不该只给 AI 的草稿做校对。人的角色是设定价值、选择权重、授权风险、提供真实状态、判断品味，并承担责任。好的 AI agent 应该只提出最小充分人类问题（Minimal Sufficient Human Query, MSHQ），而不是把整个任务推回给人。

### 让长程行动落在硬状态上

对需要长期推进的 agent 来说，计划、工具调用、观测、验证结果、人类回答和审计发现都应该进入外部硬状态，而不是只停留在聊天上下文里。在状态治理智能体范式（State-Governed Agent Regime, SGAR）下，“完成”必须经过证据与验证，不能由 agent 的自我叙事来宣布。
:::

实践中，困难任务通常不该直接写成最终文本，而应先经过一组中间对象：

```text
输入 -> 任务模型 -> 控制对象（GKO / GEsO / MSHQ） -> 硬状态（SGAR） -> 验证 / 审计 -> 最终答案
```

这些对象可以是评分规约、状态矩阵、硬状态 ledger、依赖图、选项集、失败模式清单、验证清单，也可以是 [GKO](/zh/glossary#gko)、[受治理升级对象（GEsO）](/zh/glossary#geso)或[最小充分人类问题（MSHQ）](/zh/glossary#mshq)。设置它们不是为了增加流程感，而是把高失配的最终输出问题，转化成更小、更能让模型发挥局部优势的操作。[审计工程](/docs/audit-engineering-failure-localization-control-space-writeback.zh-CN.md)则把每一次失败信号结构化为控制增量，让下一轮搜索不再犯同样的错。若想把这条运行时链路放到可量化的框架里看，可以继续读 [Agent Harness Framework](/docs/agent-harness-framework.zh-CN.md)。

## 这个项目接下来会做什么

- **公共解释层**：让没读过论文的人也能理解 LLM 平庸、局部对齐和 LLM 卓越。
- **理论层**：展开[六类原始失配](/zh/glossary#six-primitive-mismatches)、[知识治理](/zh/glossary#knowledge-governance)、[GKO](/zh/glossary#gko) / [GExO](/zh/glossary#gexo) / [GEsO](/zh/glossary#geso) / [MSHQ](/zh/glossary#mshq)、[状态治理智能体范式（SGAR）](/zh/glossary#sgar)、审计工程，以及它们在运行时的可量化关系，详见 [价值保存结构理论](/docs/structural-theory-value-preservation-llm-systems.zh-CN.md)、[受治理 LLM 对象模型与接口规范](/docs/governed-llm-object-model-interface-specification.zh-CN.md) 与 [Agent Harness Framework](/docs/agent-harness-framework.zh-CN.md)。
- **工程层**：沉淀工具与模板，把控制对象、硬状态 ledger、验证循环和最小人类接入点落到真实任务中。
- **协作层**：把人从事事经手的处理者，上移为价值、权限、品味、预算、证据和责任的治理者，详见 [治理式人机协作](/docs/governed-human-ai-collaboration.zh-CN.md) 与 [人类协助型操作失配](/docs/human-assist-operational-mismatches.zh-CN.md)。

这个项目欢迎贡献案例、批评和改进建议。

特别欢迎这些类型的贡献：

- **真实任务案例**：哪些任务里 LLM 表面表现很好，但最终价值不稳定。
- **工程模式**：你是怎样把任务拆成控制对象、验证对象、评分规约或人类决策点的。
- **失败样本**：哪些 prompt、agent 或 workflow 看起来合理，但最后被证明不可控。
- **概念修正**：针对“LLM 平庸”“局部对齐”“失配”“控制空间”“GKO / GExO / GEsO / MSHQ”“SGAR”“审计工程”等概念，提出反例、补充或更清晰的表述。
- **工具实现**：能把这些治理动作落到代码、模板、评估器或工作流里的最小组件。

贡献不需要一开始就完整。一个具体失败案例、一段可复现流程、一个更准确的术语，或者一次有证据的反驳，都比泛泛而谈更有价值。
